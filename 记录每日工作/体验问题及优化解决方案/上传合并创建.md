问题本质：
createProject和upload是两个独立的请求，两个独立的事务。用户在弹窗里创建成功，上传失败后重试，就会再次新建一个项目。由于是两个请求所以不是加锁就能够解决的问题，加锁只能防止并发双击，防不了失败重试。根源是事务边界错误。

设计：
1. 把事务边界上移到用例层， 新增编排服务 ProjectCreationServiceImpl.java:44，把"建项目 + 落盘 + 解压 + 扫描"当成**一个用例**。但它**不能**用 `@Transactional` —— 因为里面包含磁盘 IO、解压、文件扫描，DB 事务管不了这些。所以用的是**补偿事务**（saga 的简化版）：正常路径不需要补偿，失败时执行反向操作。
2. 校验前置： 第 49–50 行先 `validateRequest` + `uploadService.validateZip`，再建项目。能快速失败的（文件名、大小、ZIP 魔数）绝不拖到造完项目之后。这就是把 `validateFile` 提升成 public 的 `validateZip` 的原因（UploadServiceImpl.java:50）。
3. **幂等键只是"防重试"，不是"锁"。** 这是关键区别：

| |锁|幂等键|
|---|---|---|
|失败后|释放，允许重试|**也必须释放**，否则重试被永久卡死|
|成功后|释放|保留结果，重复请求**回放**原结果|

实现（第 52–61 行）：

- key = `idem:project:{userId}:{client-uuid}`，前端每次**打开弹窗**生成一个新 UUID，失败时保留复用（`NewProjectModal.jsx:93` 的注释）。
- `SETNX` 占坑，值为 `"IN_PROGRESS"`，TTL 10 分钟 —— 原子占位，防并发。
- 成功：把值改写成 `projectId`；失败：`delete(key)`。
- 重复请求进来（`replayOrReject`，第 89 行）：值不是 `IN_PROGRESS` 就按 projectId 查库，**还要校验 `userId` 一致**，然后返回原项目；仍是 `IN_PROGRESS` 就拒绝。

4. 回滚：失败时调用deleteProjectData，它被从 `deleteProject` 里抽出来（ProjectServiceImpl.java:88），一次清干净：`project_source` / `file` / `project_overview` / `project` 四张表 + 磁盘工作区 + Redis overview 缓存 + Python 侧 Agent Context。删除项目和创建失败走**同一段**清理逻辑，不会出现两套行为。

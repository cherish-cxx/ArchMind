问题本质：
`POST /analyze` 是**异步投递**，返回的是 `TaskResponse`，前端却把它当 `ProjectOverviewResponse` 塞进 `setOverview` 然后结束 —— 类型上就是错的，所以页面永远"待分析"。**状态的真相在后端 task 表，前端不能自己猜。**

设计决策：
**(a) 职责切开。** `runAnalyze` 只负责投递并拿到 `taskId`，然后交给轮询器（`App.jsx` 新逻辑）：`SUCCESS` 同步返回的直接处理，`PENDING/RUNNING` 一律 `startTaskPolling`。**绝不再把 TaskResponse 当 overview**。

**(b) 轮询器做成独立状态机**，而不是散在组件里的 `setTimeout`：useTaskPolling.js 只暴露 `start / resume / stop / task`，业务侧只注册四个回调 `onUpdate / onSuccess / onPartial / onFailure`。好处是这四个终态在**两处调用**（新提交、进页面恢复）复用同一套语义。

**(c) 退避曲线是产品判断，不是技术炫技**：1.5s（前 20s）→ 3s（20s 后）→ 5s（60s 后），15 分钟硬超时。前 20 秒用户正盯着看，短间隔满足"3s 内更新"的验收；之后只是兜底看门狗。

**(d) 竞态用序号收口。** `seqRef` 单调递增，`openProject / switchProject / stop` 时 `++`；在途响应回来先比对 seq，不等就丢弃。这比 `AbortController` 简单，且能覆盖"轮询已经发出去但用户切了项目"这种 fetch 取消不掉的情况。

**(e) 恢复不是重放。** `resume(projectId)` 先拉 `tasks/latest`：**只有 PENDING/RUNNING 才重新开轮询**；拿到终态只返回给调用方，不触发回调 —— 否则每次进项目页都会弹一次历史错误。这是"恢复现场"和"重演历史"的边界。

**(f) 网络抖动不终止。** `catch` 里只跳过本次、继续退避（第 61–64 行）。分析任务在后端线程池里跑着，前端一次 502 不该判定失败。

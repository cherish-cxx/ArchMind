# 开发路线图（四层认知版）

> 更新时间：2026-08-21
> 目标：把用户上传的 Java 项目解析成**四层业务认知结构**，Agent 作为「导游」基于这四层自由讲解，公网可用、多用户。

---

## 项目定位（一句话方向）

> **不是「代码问答」（Cursor 已有），而是「代码 → 业务认知」**：领域地图 + 关系图 + 导游式讲解。

**五大板块**：

1. **项目概况**：技术栈 / 是什么项目 / 概述
2. **业务领域**：领域地图 → 子业务（用户中心 · 订单 · 支付 …）
3. **系统架构**（DDD 分层视图）：业务层 / 用户入口层 / 领域模块层 / 基础设施 / 外部依赖
4. **代码探索**：领域下的代码文件 + 调用/依赖关系 + 内容简要描述
5. **AI 助手**：独立板块 + 融入各页面，随时可用

**两个正交维度**（同一份代码有两个标签）：

| 维度 | 切法 | 例 |
| --- | --- | --- |
| 业务归属 | 属于哪个领域/子业务 | 用户中心 → 登录 |
| 架构分层 | 属于哪一层 | 用户入口层 / 业务层 / 领域模块层 / 基础设施 / 外部依赖 |

例：`UserController` = 领域[用户中心] + 层[用户入口层]；`UserMapper` = 领域[用户中心] + 层[基础设施]

**核心架构：先分析、后问答**
- 重活（AST + LLM 分析）只在**上传时做一次**，产出四层结构化数据存库；
- Agent 运行时**不重新分析**，只「查地图」——这大幅降低 Agent 推理难度（把开放推理变成受限导航）。
- **两层检索（GraphRAG 混合）**：向量检索解决「语义入口」（问题措辞与库中名称不吻合时定位正确节点），图遍历解决「关系展开」（从入口沿 CALLS/IN_DOMAIN 边展开）。二者互补，缺一不可。

## 双库架构（MySQL + Neo4j）

| 数据库 | 存什么 |
| --- | --- |
| **MySQL** | user / project / file / ai_analysis_task（关系数据，多租户隔离） |
| **Neo4j** | code_element / code_relation / business_domain / capability（图数据） |

**Neo4j 节点与边**：
- 节点：File、Class、Method、Domain（领域）、Capability（子业务）
- 边：CALLS（调用）、EXTENDS / IMPLEMENTS（继承/实现）、DEPENDS（依赖）、IN_DOMAIN（属于领域）、HAS_CAPABILITY（对应能力）

> Neo4j 在 **P1 随 AST 一起引入**（AST 一产出关系数据就直接进图库，避免「先存 MySQL 再迁移」的返工）。

## 核心架构决策：统一任务系统（解决「分析管道异步」缺口）

分析任务（上传后流水线）与问答任务（Agent 循环）本质相同，**用一套统一任务系统，不做两套**。

**三个核心决策**：

1. **上传 / 分析解耦**：上传是同步快动作（解压 + 落盘 + 文件树）；分析是异步、可重跑动作（改代码后重新 analyze，无需重传）。
2. **阶段化流水线**：分析任务分 8 阶段——文件扫描 → AST 提取 → 概况 → 领域拆分 → 架构分层 → 子业务 → 描述 → embedding；进度 = 当前阶段 + 阶段内进度。
3. **阶段级失败处理**：加 `PARTIAL` 状态；失败阶段单独重试；已成功阶段结果复用（幂等，省 LLM 钱）。

**任务表（MySQL）**：

| 字段 | 说明 |
| --- | --- |
| id / project_id / user_id | 归属 |
| type | ANALYSIS / QA |
| status | PENDING / RUNNING / SUCCESS / PARTIAL / FAILED |
| progress | 0–100 |
| current_stage | 分析用（如 "AST"），问答为空 |
| detail | JSON（分析=各阶段结果；问答=Agent 步骤） |
| error | 失败原因 |

**执行模型**：单机线程池（4–8 线程）+ 轮询，**不引 MQ**（实验室规模用不上；MQ 只在多实例/高负载才需要）。

状态机：`PENDING → RUNNING → SUCCESS / PARTIAL / FAILED`

- [ ] 流式输出 SSE（可选，体验加分）

**成本策略（先配额，后 BYOK）**：
- [ ] token 计量：每次 LLM 调用统计 input/output token，记录消耗
- [ ] 免费配额：quota 表（remaining_tokens / reset_time），每用户定量，不足则拒绝并提示
- [ ] BYOK（用户自填 key）：user 表加 api_key_encrypted（AES 加密）/ api_key_provider / api_key_masked，密钥走环境变量，日志与响应永不下发完整 key
- [ ] LLM 调用层统一解析：有用户 key 且操作受支持 → 用用户 key 不扣配额；否则 → 平台 key 扣配额
- [ ] embedding 回退：用户 key 不支持 embedding 时回退平台 key 或降级关键词

**验收**：问「这个项目怎么用」→ agent 从登录开始串讲各功能，附领域和代码跳转

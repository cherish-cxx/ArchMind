# 开发路线图（四层认知版）

> 更新时间：**2026-10-21**（闭环已通，进入体验修复与工程化阶段）
> 目标：把用户上传的 Java 项目解析成**四层业务认知结构**，Agent 作为「导游」基于这四层自由讲解，公网可用、多用户。
> **当前阶段：大三上** —— 目标窗口是 **2027/03–05 的暑期实习投递**，不是临阵。节奏与优先级见 [实习准备节奏表](实习准备节奏表.md)。
> **当前状态**：上传 → 分析 → 图谱 → Agent 问答 → 画布操控的闭环已跑通；但真实使用后暴露了 7 个体验问题，且"只像调了一次 LLM"的体感仍未解决。下一阶段主线：**体验修复 → 表达层 → 画布 → 语义入口 → 记忆 → 多步 Agent → 认知层**（见 R1–R8）。

## 项目定位（一句话方向）

> **不是「代码问答」（Cursor 已有），而是「代码 → 业务认知」**：领域地图 + 关系图 + 导游式讲解。

**五大板块**：

1. **项目概况**：技术栈 / 是什么项目 / 概述
2. **业务领域**：领域地图 → 子业务（用户中心 · 订单 · 支付 …）
3. **系统架构**（DDD 分层视图）：业务层 / 用户入口层 / 领域模块层 / 基础设施 / 外部依赖
4. **代码探索**：领域下的代码文件 + 调用/依赖关系 + 内容简要描述
5. **AI 助手**：独立板块 + 融入各页面，随时可用

**两个正交维度**（同一份代码有两个标签）：

| 维度 | 切法 | 例 |
| --- | --- | --- |
| 业务归属 | 属于哪个领域/子业务 | 用户中心 → 登录 |
| 架构分层 | 属于哪一层 | 用户入口层 / 业务层 / 领域模块层 / 基础设施 / 外部依赖 |

例：`UserController` = 领域[用户中心] + 层[用户入口层]；`UserMapper` = 领域[用户中心] + 层[基础设施]

**核心架构：先分析、后问答**
- 重活（AST + LLM 分析）只在**上传时做一次**，产出四层结构化数据存库；
- Agent 运行时**不重新分析**，只「查地图」——这大幅降低 Agent 推理难度（把开放推理变成受限导航）。
- **两层检索（GraphRAG 混合）**：向量检索解决「语义入口」（问题措辞与库中名称不吻合时定位正确节点），图遍历解决「关系展开」（从入口沿 CALLS/IN_DOMAIN 边展开）。二者互补，缺一不可。

## 核心架构决策：Java + Python 两服务 ★

**按数据所有权切，不按语言切。**（一个服务 = 一份数据的所有权 + 一个变更的理由）

| 关注点 | Java（code-intelligence） | Python（agent） |
| --- | --- | --- |
| MySQL 业务数据 | ✅ 独占 | ❌ 不连 |
| Neo4j 代码图 | ✅ 独占 | ❌ 不连 |
| 源码文件磁盘 | ✅ 独占 | ❌ 不读 |
| `task` 表（ANALYSIS） | ✅ 独占 | ❌ |
| LLM 调用 | 暂留（分析流水线） | ✅ 新增全部在此 |
| 会话 / Context / 步骤日志 | ❌ | ✅ 独占（Redis db1） |
| JWT / 用户 / 租户校验 | ✅ 独占 | ❌ 只接收已校验的 projectId |

**三条硬规则**：

1. **Python 不直连 Neo4j / MySQL** —— 共享数据库 = 分布式单体；且会绕过 Java 的租户校验（越权读别家项目代码）。Python 要数据，走 Java 的 `/internal/tools/*`。
2. **JWT 永远不进 Python** —— 入口留在 Java，token 在 Java 层被换成「已校验的 projectId」再下传。副作用是白拿的安全收益：token 不可能被拼进 LLM prompt 或写进 Python 日志。
3. **鉴权必须留在数据主人那** —— 认证（验 token 签名）只需密钥，可以前置到网关；**鉴权（这个项目属不属于这个用户）需要查数据，必须留在 Java**。

**调用链**：

```
前端 → Java（JWT + 租户校验）→ Python（Intent / 工具编排 / LLM）→ Java（/internal/tools/* 取数）
```

**工具的「两个半边」**：Java 提供**执行**（Cypher / 文件切片），Python 提供**契约 + 编排**（给 LLM 的 schema 与调度）。**5 个工具，不是 10 个**；Java 侧对"Agent"这件事一无所知。

> 完整设计（闭环时序、接口契约、反模式清单、演进路线）见 [9月19 Agent v1 设计](开发过程/9月19%20Agent%20v1设计.md)。

| 数据库 | 存什么 | 归属 |
| --- | --- | --- |
| **MySQL** | user / project / project_source / file / project_overview / project_dependency / task | Java 独占 |

**Neo4j 现状**（2026-09-12 起）：

- 节点：`:Class`（uid = 全限定名）、`:Method`（uid = `owner#signature`），均带 `projectId + fileId + startLine/endLine`
- 边：`CALLS`（带 count）、`EXTENDS`、`IMPLEMENTS`、`DEPENDS`（带 via）
- 约束：复合 `UNIQUE (projectId, uid)` —— **社区版禁 `NODE KEY`（企业版专属）**，以后别再碰
- 规划中：`Domain` / `Capability` 节点 + `IN_DOMAIN` / `HAS_CAPABILITY` 边（R8）

## 核心架构决策：统一任务系统（解决「分析管道异步」缺口）

分析任务（上传后流水线）与问答任务（Agent 循环）本质相同，**用一套统一任务系统，不做两套**。

**三个核心决策**：

1. **上传 / 分析解耦**：上传是同步快动作（解压 + 落盘 + 文件树）；分析是异步、可重跑动作（改代码后重新 analyze，无需重传）。
2. **阶段化流水线**：分析任务分阶段——文件扫描 → AST 提取 → 概况 → 核心类描述（→ R4 加 embedding 索引；R8 加领域拆分 / 架构分层 / 子业务）；进度 = 当前阶段 + 阶段内进度。
3. **阶段级失败处理**：加 `PARTIAL` 状态；失败阶段单独重试；已成功阶段结果复用（幂等，省 LLM 钱）。

**任务表（MySQL）**：

| 字段 | 说明 |
| --- | --- |
| id / project_id / user_id | 归属 |
| type | ANALYSIS / QA |
| status | PENDING / RUNNING / SUCCESS / PARTIAL / FAILED |
| progress | 0–100 |
| current_stage | 分析用（如 "AST"），问答为空 |
| detail | JSON（分析=各阶段结果；问答=Agent 步骤） |
| error | 失败原因 |

**执行模型**：单机线程池（4–8 线程）+ 轮询。

> **关于 `QA` 类型**：`TaskType.QA` 常量已存在，但 **Agent 的 QA 链路 V1 不走 task 表** —— 两者生命周期完全不同（ANALYSIS 是幂等可重跑的重活；QA 是有状态的短会话）。QA 的步骤日志由 Python 侧的会话存储保管。
>
> **MQ 的演进点**：把 `analyze` 从线程池改为 MQ 驱动是**真实需求**（任务可靠投递、失败重试、削峰），不是硬塞。作为大三上的学习项，见节奏表 §3。

状态机：`PENDING → RUNNING → SUCCESS / PARTIAL / FAILED`

### P2.6 体验验收问题（2026-10-21 实测，必须先修）

| # | 现象 | 根因（已定位到代码） | 修法 | 工时 |
| --- | --- | --- | --- | --- |

## R 系列：2026-10-21 起的实施阶段

> 旧的宏观 P3/P4/P5 已分别映射为 R8/R9/R10（注意与 P2 小节里 Agent 执行步骤的 P0–P4 是两套编号）；**时间以 R 系列为准**。

### R1 体验修复（2026/10/21–11/03）

**目标**：把 P2.6 的 1/2/4 修掉，并补上"点节点看代码"。

- [ ] 上传：nginx 限制、前端预检与进度、合并创建+上传、失败清理、幂等键
- [ ] 分析状态：`useTaskPolling` + `tasks/latest` 恢复；PARTIAL/FAILED 可读
- [ ] 语言归类：category 归一化 + 前端兼容 + `file.language` 兜底

- [ ] 补 5 条 golden question（为 R4 评测打底）

**技术栈**：nginx、Spring、React、Shiki
**验收**：500MB 上传有明确上限提示；重试不产生重复项目；状态 3s 内自动更新；点任意类能看到源码

### R2 回答表达（11/04–11/17）

**目标**：回答从"一段话"变成"有结构、有重点、有引用"。

- [ ] 讲解输出改结构化：`headline + sections[{title, body, citedUids}] + nextSteps`，保留 `message` 兜底
- [ ] Markdown 渲染 + 排版 CSS + 代码块高亮；内容区限宽左对齐
- [ ] prompt 改造：受众 = 刚接手项目的同学；先结论、再路径、再证据；禁止只罗列类名
- [ ] 讲解 prompt 注入 project overview / 模块 / 技术栈作为业务上下文
- [ ] 引用 chip 可点击跳节点；sections 内的 uid 同样过 evidence 校验

**技术栈**：react-markdown、remark-gfm、rehype-sanitize、Shiki
**验收**：20 个问题输出均有标题层级与重点；无裸 JSON；每条引用都能追溯到 evidence
**工时**：约 24h

### R3 画布 v2（11/18–12/01）

**目标**：让图"看得出结构"，而不是一团线。

- [ ] 关系视觉编码：CALLS 实线 / DEPENDS 虚线 / EXTENDS 粗实线空心箭头 / IMPLEMENTS 点线空心箭头；图例 + 可开关
- [ ] 节点卡片：类名、包名、2 行描述、关系数、断链标记；点击打开代码抽屉
- [ ] 布局：先按 package/module 聚块，块内 depth/radial；跨块曲线、块内直线
- [ ] "单关系视图"切换（等价于四个面板，但不复制节点）
- [ ] 200 节点以上：视口裁剪 / 按模块折叠
- [ ] 保持确定性坐标（刷新不跳、增量不重排）

**技术栈**：SVG、ELK.js（compound/layered）或自写分区布局
**验收**：四种关系一眼可分；200 节点布局 < 500ms；刷新与增量后已有节点坐标不变
**工时**：约 30h

### R4 语义入口 + 评测基线（12/02–12/15）

**目标**：不点类也能问；第一次有可量化的质量数字。

- [ ] 实体卡片：Class/Method 的名称、包、签名、描述、上下游一句话
- [ ] Embedding：本地 `bge-m3`（备选 Qwen `text-embedding-v3`）
- [ ] 向量库：**Qdrant（Python 独占）**；索引是派生数据，Java 仍是图的主人；分析完成后回调 `/internal/index/build`
- [ ] 混合检索：向量 + 名称/包关键词 + 图度数先验；可选 rerank
- [ ] 锚点消歧：候选给 LLM 选；选不准就回澄清（复用现有低置信路径）
- [ ] 评测集：30–50 条「问题 → 正确锚点类」；指标 recall@5 / MRR / citation grounding / gap disclosure / P50·P95 / token
- [ ] 评测脚本一键跑，结果落 JSON，改 prompt 前后对比

**技术栈**：bge-m3、Qdrant、FastAPI、pytest
**验收**：自由提问 anchor recall@5 ≥ 80%；评测报告可重复生成
**工时**：约 30h

### R5 持久化 + 记忆 v1（12/16–12/29）

**目标**：会话不再靠 Redis TTL 续命；"重点记忆"能跨会话召回。

- [ ] MySQL 表：`agent_conversation` / `agent_turn` / `agent_memory`
- [ ] Python 独占（与 Context 所有权一致）；SQLAlchemy 2.0 async + Alembic
- [ ] Redis 继续做热缓存，MySQL 做真相；启动/换 worker 可恢复
- [ ] 记忆分层：工作记忆（Redis，不向量化）/ 情节记忆 / 重点记忆（pinned）
- [ ] 写路径：每轮确定性蒸馏 episode；用户显式"记住"→ pinned；LLM 提议必须过 evidence
- [ ] 记忆检索：user + project + ACTIVE 过滤 → 向量 + 时间 + 重要性；注入"背景（可能过时）"
- [ ] 记忆不进 citations；`graph_rev` 变化后校验 uid，失效标 STALE
- [ ] 租户隔离在 SQL 层，不在 prompt 层

**技术栈**：MySQL、SQLAlchemy 2.0、Alembic、Qdrant（独立 collection）
**验收**：重启后会话仍在；新会话能召回旧结论；跨租户测试无泄漏
**工时**：约 30h

### R6 多步 Agent + SSE（12/30–01/12）

**目标**：从"一次查询"变成"一次调查"。

- [ ] 有界 ReAct：planner 看 evidence 摘要决定下一步；硬预算（4 步 / 6 次工具）
- [ ] 去重与终止条件：同一 uid + 同一工具不重复；信息足够即停
- [ ] 失败路径：工具失败降级、断链后自动补查（接口 → method-body → 实现类）
- [ ] `steps` 增加 PLAN 类型；前端展示"调查轨迹"
- [ ] SSE：Python → Java（ResponseBodyEmitter/WebFlux）→ 前端流式渲染
- [ ] 不重写核心循环；**不引入 LangGraph 重写**（见技术决策记录）

**技术栈**：自研状态机、SSE
**验收**：一轮可见 2–4 次工具调用；断链能自动补查；SSE 首 token < 2s
**工时**：约 30h

### R7 MCP Server + 演示（寒假前两周）

**目标**：从"一个网站"变成"别的 agent 的上下文层"。

- [ ] Python `mcp` SDK（FastMCP）暴露：`list_projects` / `overview` / `search_entities` / `call_chain` / `class_relations` / `method_body`
- [ ] 鉴权：项目域 PAT（不是内部共享 token）；Java 校验 `userId + projectId`
- [ ] 只暴露白名单工具，**不暴露任意 Cypher**

- [ ] 用 Claude Code 实机演示：让它通过 ArchMind 讲 hmall 的下单流程

**技术栈**：MCP Python SDK、PAT、Redis 限流
**验收**：Claude Code 能连上并基于图回答，回答里能看到 tool 调用
**工时**：约 20h

### R8 认知层：领域 + 子业务 + 架构分层（原 P3，寒假，★最难）

**目标**：把"类图"升级成"业务地图"——这是与 Cursor 的分界线。

**技术栈**：igraph + leidenalg（社区发现）、LLM（命名/合并/校验）、Neo4j、Embedding（bge-m3）

**路线修正（2026-10-21）**：**不要让 LLM 从零聚类**。先在类依赖图上做社区发现，package 结构做先验，LLM 只负责命名、合并、淘汰；每个领域/能力必须挂到真实 uid 上，对不上账就丢。

- [ ] 社区发现：导出 class 依赖子图 → Leiden 分区 → 候选模块
- [ ] package/命名先验：同一包、同前缀的类作为强约束
- [ ] LLM 命名与合并：只处理候选块，不生成新节点
- [ ] **对账**：LLM 输出里每个类回图库查证；未命中的丢弃或降置信
- [ ] 领域生成：`Domain` 节点 + `IN_DOMAIN` 边
- [ ] 子业务生成：每个领域内拆 `Capability` + `HAS_CAPABILITY` 边
- [ ] 架构分层：入口层/业务层/领域模块层/基础设施/外部依赖（包名/注解规则 + LLM 兜底）
- [ ] 外部依赖：pom + import 包名 → 依赖清单与分层
- [ ] 领域/能力 embedding：供"业务入口"检索
- [ ] 领域地图可视化（复用 R3 的分组布局）

> ⚠️ **R8 之前，"模块"仍是 LLM 只看 pom + README 编出来的假节点**（无 ID、无 `module→class` 边、keyFiles 未对账）——Agent 的入口必须仍是「类」。

**全局最大风险点**：社区划分粒度 + 对账逻辑 + 图规模。策略：先在 hmall + demo 两个项目上做对，再谈通用。
**验收**：领域图里每个节点都能追溯到真实 uid；人工抽查 20 个类的归属，错分 ≤ 10%。
**工时**：4–6 周（寒假主线）

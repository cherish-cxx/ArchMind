# 开发路线图（四层认知版）

> 更新时间：**2026-09-19**（配合 [实习准备节奏表](实习准备节奏表.md) 重排）
> 目标：把用户上传的 Java 项目解析成**四层业务认知结构**，Agent 作为「导游」基于这四层自由讲解，公网可用、多用户。
> **当前阶段：大三上** —— 目标窗口是 **2027/03–05 的暑期实习投递**，不是临阵。节奏与优先级见 [实习准备节奏表](实习准备节奏表.md)。

## 项目定位（一句话方向）

> **不是「代码问答」（Cursor 已有），而是「代码 → 业务认知」**：领域地图 + 关系图 + 导游式讲解。

**五大板块**：

1. **项目概况**：技术栈 / 是什么项目 / 概述
2. **业务领域**：领域地图 → 子业务（用户中心 · 订单 · 支付 …）
3. **系统架构**（DDD 分层视图）：业务层 / 用户入口层 / 领域模块层 / 基础设施 / 外部依赖
4. **代码探索**：领域下的代码文件 + 调用/依赖关系 + 内容简要描述
5. **AI 助手**：独立板块 + 融入各页面，随时可用

**两个正交维度**（同一份代码有两个标签）：

| 维度 | 切法 | 例 |
| --- | --- | --- |
| 业务归属 | 属于哪个领域/子业务 | 用户中心 → 登录 |
| 架构分层 | 属于哪一层 | 用户入口层 / 业务层 / 领域模块层 / 基础设施 / 外部依赖 |

例：`UserController` = 领域[用户中心] + 层[用户入口层]；`UserMapper` = 领域[用户中心] + 层[基础设施]

**核心架构：先分析、后问答**
- 重活（AST + LLM 分析）只在**上传时做一次**，产出四层结构化数据存库；
- Agent 运行时**不重新分析**，只「查地图」——这大幅降低 Agent 推理难度（把开放推理变成受限导航）。
- **两层检索（GraphRAG 混合）**：向量检索解决「语义入口」（问题措辞与库中名称不吻合时定位正确节点），图遍历解决「关系展开」（从入口沿 CALLS/IN_DOMAIN 边展开）。二者互补，缺一不可。

## 核心架构决策：Java + Python 两服务 ★

**按数据所有权切，不按语言切。**（一个服务 = 一份数据的所有权 + 一个变更的理由）

| 关注点 | Java（code-intelligence） | Python（agent） |
| --- | --- | --- |
| MySQL 业务数据 | ✅ 独占 | ❌ 不连 |
| Neo4j 代码图 | ✅ 独占 | ❌ 不连 |
| 源码文件磁盘 | ✅ 独占 | ❌ 不读 |
| `task` 表（ANALYSIS） | ✅ 独占 | ❌ |
| LLM 调用 | 暂留（分析流水线） | ✅ 新增全部在此 |
| 会话 / Context / 步骤日志 | ❌ | ✅ 独占（Redis db1） |
| JWT / 用户 / 租户校验 | ✅ 独占 | ❌ 只接收已校验的 projectId |

**三条硬规则**：

1. **Python 不直连 Neo4j / MySQL** —— 共享数据库 = 分布式单体；且会绕过 Java 的租户校验（越权读别家项目代码）。Python 要数据，走 Java 的 `/internal/tools/*`。
2. **JWT 永远不进 Python** —— 入口留在 Java，token 在 Java 层被换成「已校验的 projectId」再下传。副作用是白拿的安全收益：token 不可能被拼进 LLM prompt 或写进 Python 日志。
3. **鉴权必须留在数据主人那** —— 认证（验 token 签名）只需密钥，可以前置到网关；**鉴权（这个项目属不属于这个用户）需要查数据，必须留在 Java**。

**调用链**：

```
前端 → Java（JWT + 租户校验）→ Python（Intent / 工具编排 / LLM）→ Java（/internal/tools/* 取数）
```

**工具的「两个半边」**：Java 提供**执行**（Cypher / 文件切片），Python 提供**契约 + 编排**（给 LLM 的 schema 与调度）。**5 个工具，不是 10 个**；Java 侧对"Agent"这件事一无所知。

> 完整设计（闭环时序、接口契约、反模式清单、演进路线）见 [9月19 Agent v1 设计](开发过程/9月19%20Agent%20v1设计.md)。

## 双库架构（MySQL + Neo4j）

| 数据库 | 存什么 | 归属 |
| --- | --- | --- |
| **MySQL** | user / project / project_source / file / project_overview / project_dependency / task | Java 独占 |
| **Neo4j** | `:Class` / `:Method`（统一 `:CodeNode` 标签） | Java 独占 |
| **Redis** | db0：overview 缓存 + 并发锁（Java）／ db1：Agent Context（Python） | 共用实例，**不共用 keyspace** |

**Neo4j 现状**（2026-09-12 起）：

- 节点：`:Class`（uid = 全限定名）、`:Method`（uid = `owner#signature`），均带 `projectId + fileId + startLine/endLine`
- 边：`CALLS`（带 count）、`EXTENDS`、`IMPLEMENTS`、`DEPENDS`（带 via）
- 约束：复合 `UNIQUE (projectId, uid)` —— **社区版禁 `NODE KEY`（企业版专属）**，以后别再碰
- 规划中：`Domain` / `Capability` 节点 + `IN_DOMAIN` / `HAS_CAPABILITY` 边（P3）

## 核心架构决策：统一任务系统（解决「分析管道异步」缺口）

分析任务（上传后流水线）与问答任务（Agent 循环）本质相同，**用一套统一任务系统，不做两套**。

**三个核心决策**：

1. **上传 / 分析解耦**：上传是同步快动作（解压 + 落盘 + 文件树）；分析是异步、可重跑动作（改代码后重新 analyze，无需重传）。
2. **阶段化流水线**：分析任务分阶段——文件扫描 → AST 提取 → 概况 → 核心类描述（→ P3 加领域拆分 / 架构分层 / 子业务 / embedding）；进度 = 当前阶段 + 阶段内进度。
3. **阶段级失败处理**：加 `PARTIAL` 状态；失败阶段单独重试；已成功阶段结果复用（幂等，省 LLM 钱）。

**任务表（MySQL）**：

| 字段 | 说明 |
| --- | --- |
| id / project_id / user_id | 归属 |
| type | ANALYSIS / QA |
| status | PENDING / RUNNING / SUCCESS / PARTIAL / FAILED |
| progress | 0–100 |
| current_stage | 分析用（如 "AST"），问答为空 |
| detail | JSON（分析=各阶段结果；问答=Agent 步骤） |
| error | 失败原因 |

**执行模型**：单机线程池（4–8 线程）+ 轮询。

> **关于 `QA` 类型**：`TaskType.QA` 常量已存在，但 **Agent 的 QA 链路 V1 不走 task 表** —— 两者生命周期完全不同（ANALYSIS 是幂等可重跑的重活；QA 是有状态的短会话）。QA 的步骤日志由 Python 侧的会话存储保管。
>
> **MQ 的演进点**：把 `analyze` 从线程池改为 MQ 驱动是**真实需求**（任务可靠投递、失败重试、削峰），不是硬塞。作为大三上的学习项，见节奏表 §3。

状态机：`PENDING → RUNNING → SUCCESS / PARTIAL / FAILED`

## 竞争力定位（诚实版）

> 对「双非 + 大三上 + 第一次做项目 + 无实习」：这是一个**能过简历关、面试有得聊**的扎实差异化项目，不是惊艳级。

- **Java 后端**：✅ 覆盖核心栈（Spring Boot 4 / MyBatis-Plus / MySQL / JWT / 异步 / Docker）+ 真实工程问题（多租户 / 上传安全 / AST）；⚠️ 缺 MQ、高并发 → 八股 + MQ 改造
- **Agent 岗**：✅ 真做了 agent（工具层设计 / ReAct 循环 / 结构化输出 / evidence 防幻觉）+ **Java + Python 双服务边界**是很好的谈资；⚠️ 生态偏 Python → 补概念八股 + 讲清「为何手动实现工具循环」「为何 Python 不直连库」
- **最大的差异化**：**「Java 后端 + Agent 应用」交叉赛道**——会写 CRUD 的人很多，能讲清服务边界与数据所有权的人少得多

存在问题：
1. 当前Python侧不直连Mysql，是通过java侧进行间接调用的。所以为了解决这个问题，需要在java和Python之间的共享密钥中加入userId的传入。
2. 当前的上下文情况：
	   进入上下文的只有用户提示词，RAG检索结果不进入上下文，只进入提示词LLM1和LLM2；LLM返回结果只有部分进入上下文（前120字）
	   并且当前所有有的内容都不会进行进入大模型的提示词中，因为会通过一个六选一的基础判断。导致目前项目没有记忆。没有agent的感觉。调用方和触发调用方都是Python
	   导致：回放不出真正的过程。无法复盘。
3. 一个上下文不是单单对一个内容进行存储，而是将当前的这个上下文的所有的内容都拆分成三份，那么如何拆分成三份？
```
agent_context   =状态
agent_turn    =流水
agent_memory  =派生
```
4. 拆分成三份后如何拼回来？


解决原理：
拆分后如何恢复上下文：
	顺序不是恢复时重新算出来的，而是写入时就作为一条补空边的属性记录下来的。
	拆成三张表之所以还能够还原是因为他们共享一个键converstion_id--关键靠键，不是物理相连
	直觉上：一份数据拆分成三份，需要靠拼才能够重新恢复，但是数据库的拆分不是这样的
```
                     conversation_id = "c_1913..."
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
  agent_conversation     agent_turn            agent_context
  (一行)                 (N 行)                (一行)
```
三张表都能够独立查询，重复的那一个是外键，拆分丢掉的不是关联，而是必须整体读写的这个约束，状态每轮覆盖时间只追加，他们本来就不应该被绑在一起读写

顺序是如何解决的：
简单理解就是：也就是等于每一轮对话，都会给这个对话标识一个值，这个值是从1开始递增的。后续只需要获得这个窗口的conversation_id然后再去扫描这个值就能够知道所有顺序然后将它遍历出来


为什么不能用一个JSON一个大字段去存整段会话？

| 问题            | 具体后果                                 |
| ------------- | ------------------------------------ |
| **写放大 O(n²)** | 第 20 轮要重写前 19 轮的内容。20 轮共写 210 轮份的数据量 |
| **并发必冲突**     | 两个人同时往同一会话发消息（两个标签页），后写的覆盖先写的        |
| **无法局部读**     | 想显示第 18 轮，得先读出 20 轮全文再解析             |
| **无法索引**      | 想查"哪些轮用了 call-chain"，只能全表扫 + JSON 解析 |
| **无法分页**      | 100 轮的会话，打开就是几 MB                    |
| **状态没法独立更新**  | viewport 上报要改状态，但它不该触发重写整个历史         |

改成一行一轮之后：

| 指标      | 大 JSON | 一行一轮                        |
| ------- | ------ | --------------------------- |
| 追加一轮    | 重写全部   | O(1)                        |
| 并发      | 冲突     | 靠 `turn_no` 串行化             |
| 读第 18 轮 | 读全部    | 索引定位                        |
| 分页      | 做不到    | `WHERE turn_no > ? LIMIT ?` |
| 状态更新    | 抢同一行   | 不同表，互不干扰                    |

三张表的分工：
agent_conversation--会话索引
用途：做烂会话列表，发号，标题，删除状态

| 字段                   | 类型             | 说明                              |
| -------------------- | -------------- | ------------------------------- |
| `id`                 | VARCHAR(64) PK | `c_19135ba5f7674d63`，前端传的那个 cid |
| `user_id`            | BIGINT         | 租户隔离第 1 维                       |
| `project_id`         | BIGINT         | 租户隔离第 2 维                       |
| `title`              | VARCHAR(120)   | 第一条用户消息截断生成，**不调 LLM**          |
| `turn_count`         | INT            | **序列计数器**：当前发到第几号。发号和列表展示都用它    |
| `graph_rev_at_start` | INT            | 会话开始时项目的图版本，用来判断"整个会话是不是基于旧图"   |
| `status`             | VARCHAR(16)    | `ACTIVE` / `DELETED`（软删）        |
| `created_at`         | DATETIME(3)    | 创建时间                            |
| `updated_at`         | DATETIME(3)    | 最后活动时间，列表按它倒序                   |

**不存什么**：任何对话内容、任何状态。它只是"目录页"。

**索引**：`(user_id, project_id, updated_at DESC)` —— 列表查询一次走完。

---
agent_turn--回合流水
用途：打开历史窗口时，回放，排查为什么这轮答错，评测集，记忆蒸馏
一轮一行，**只插入，不更新**。

### 2.1 定位

|字段|类型|说明|
|---|---|---|
|`id`|BIGINT AUTO PK|代理主键|
|`conversation_id`|VARCHAR(64)|属于哪个会话|
|`user_id`|BIGINT|冗余，为了租户过滤直接走索引|
|`project_id`|BIGINT|冗余，同上|
|`turn_no`|INT|**会话内序号**，1 开始，永不变|

唯一索引：`(conversation_id, turn_no)`

### 2.2 输入（用户这一轮说了什么）

|字段|类型|说明|
|---|---|---|
|`question`|TEXT|用户原话，原文不动|
|`rewritten_query`|TEXT|LLM#1 消解代词后的问句，可为空|
|`focus_before`|VARCHAR(512)|这轮开始前的锚点 uid|
|`method_uid`|VARCHAR(512)|锁定的方法，可为空|

### 2.3 判定（系统怎么理解这一轮）

|字段|类型|说明|
|---|---|---|
|`intent`|VARCHAR(32)|六个意图之一|
|`confidence`|DECIMAL(4,3)|0.000 ~ 1.000|
|`degraded`|TINYINT(1)|是否走了规则降级|
|`outcome`|VARCHAR(16)|**这一轮走到哪个分支**：`OK` / `CLARIFY` / `NAVIGATE` / `REFUSE` / `NEED_ANCHOR` / `TOOL_DOWN` / `TOOL_NO`|

`outcome` 是**新增的关键字段**。没有它，澄清轮、拒绝轮、工具失败轮在历史里就消失了。

### 2.4 中间产物（JSON）

|字段|内容|
|---|---|
|`retrieval_json`|RAG 检索结果|
|`tool_calls_json`|这一轮所有工具调用|
|`evidence_json`|本轮可引用 uid 白名单|

**`retrieval_json` 的样子**：

```
{  "attempted": true,  "partial": false,  "reason": null,  "candidates": [    { "uid": "com.example.AnalysisController", "score": 0.83,      "simpleName": "AnalysisController", "kind": "CLASS",      "description": "项目分析入口" }  ]}
```

**`tool_calls_json` 的样子**：

```
[  {    "tool": "call-chain",    "args": { "uid": "com.example.AnalysisController", "direction": "DOWN", "depth": 3 },    "ok": true,    "truncated": false,    "note": null,    "graphRev": 7,    "ms": 45,    "data": { "start": {...}, "nodes": [...], "gaps": [...] },    "evidence": [      { "kind": "EDGE", "from": "A", "to": "B", "rel": "CALLS", "count": 1 }    ]  }]
```

注意 `graphRev` 是**每个工具调用各自**的版本——一轮里可能既有基于新图的调用，也有基于旧图的（缓存），所以不能只存在 `agent_turn.graph_rev` 一个地方。

**`evidence_json` 的样子**：

```
["com.example.AnalysisController", "com.example.Result", "com.example.FileController"]
```

它就是 `citedUids` 的白名单，存下来才能事后校验"当时那句话有没有出处"。

### 2.5 输出（系统答了什么）

|字段|类型|说明|
|---|---|---|
|`answer_message`|MEDIUMTEXT|最终 Markdown 正文（降级时是模板文本）|
|`headline`|VARCHAR(200)|一句话结论，可为空|
|`sections_json`|JSON|分段结构化讲解（每段有 title / body / citedUids）|
|`citations_json`|JSON|扁平引用列表，`sections` 的并集|
|`ui_commands_json`|JSON|当时生成的出图命令（**回放时不执行，只展示**）|
|`graph_patch_json`|JSON|这一轮的子图数据，用于只读预览|
|`steps_json`|JSON|调查轨迹：意图耗时、检索、工具耗时、讲解耗时|

**为什么 `sections_json` 和 `citations_json` 都存**：`sections` 是真相，`citations` 是给旧前端/Java 网关用的扁平视图。两者是同一份数据的两种视图，不冲突。

### 2.6 运维

|字段|说明|
|---|---|
|`graph_rev`|这一轮结束时项目的图版本|
|`latency_ms`|整轮耗时|
|`payload_bytes`|这一行实际多大，用来监控膨胀|
|`truncated`|超上限被截断（`tool_calls_json` 太大时）|
|`created_at`|写入时间（**只用于排查，不用于排序**）|

**不存什么**：

- 不存 `focus_stack` 当时的内容（只有 `focus_before`）
- 不存逐轮的 viewport 快照
- 不存 LLM 原始返回文本（除非单开调试表）

`agent_context` —— 状态快照

**用途**：用户继续对话时，把"现在该是什么状态"装回去；刷新页面时恢复屏幕。

一个会话一行，**每轮覆盖**。

|字段|类型|说明|
|---|---|---|
|`conversation_id`|VARCHAR(64) PK|一个会话只有一份状态|
|`user_id`|BIGINT|租户过滤|
|`project_id`|BIGINT|租户过滤|
|`state_json`|JSON|`AgentContext` 的完整序列化|
|`model_version`|INT|对应 `AgentContext.version`，反序列化失败时用来判"该重建"|
|`updated_at`|DATETIME(3)|最后覆盖时间|

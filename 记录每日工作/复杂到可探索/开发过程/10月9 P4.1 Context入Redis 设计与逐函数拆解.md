## 第一部分 · 设计思路（为什么这么做）

### 1. 要解决的真问题

P3 的 Context 存在一个**进程级 dict** 里（`_CONTEXTS`）。它有三个后果，**按严重程度排**：

| # | 后果 | 严重度 |
|---|---|---|
| 1 | **多 worker 时静默串会话** | ★★★ 真 bug |
| 2 | 进程重启即丢 | ★★ 体验问题 |
| 3 | 删项目时清不干净 | ★ 运维问题 |

**第 1 条是最要命的，也是最容易被忽略的**：生产上 uvicorn 会起多个 worker，**每个 worker 一份自己的 dict**。

```
用户第 1 轮 → worker A  → A 建了 Context
用户第 2 轮 → worker B  → B 没有这个 Context，当成新会话
用户看到：聊到一半突然失忆，而且不报错
```

开发时 `--reload` 是单进程，所以你**测不出来**；一上多 worker 立刻坏。

> **关键认知**：这不是「换个存储」的问题，是「**状态放错了位置**」的问题。
> 会话状态天生属于「多个进程要共享」，却放在了「只有单个进程能看见」的地方。

### 2. 为什么是 Redis db1

#### 2.1 为什么不让 Python 直接连数据库（共享 MySQL）

这是最先要排除的方案。四条理由，实质是**两条**：

- **一致性**：Python 侧解析出的数据和数据库里实际更新后的内容可能对不上。
- **隔离性**：Python 没有 JWT 校验，让它直连数据库等于绕开了用户身份这道门。

所以架构上定死：**Python 不碰数据库**，所有数据只能通过 Java 的 `/internal/tools` 拿。Context 是 Python 自己的**运行时状态**（不是数据），所以它可以自己存，但只能存在「Python 自己的一块地方」。

#### 2.2 为什么是 **db1** 而不是 db0

服务器上**已经有一个 Redis 了** —— Java 侧的 overview 缓存，`application.yml` 里写的是 `database: 0`。

```
同一个 Redis 实例 172.21.160.203:6379
├── db0  ← Java 的 overview 缓存（可丢，丢了重算）
└── db1  ← Python 的 Context（主存储，丢了等于对话结束）
```

**为什么要隔开**：两者语义完全不同 —— 一个是缓存（丢了无所谓），一个是主存储（丢了有所谓）。混在一个 db 里，你将无法对它们施加不同的策略（比如内存告急时的处置）。

**顺带一个好消息**：实测服务器 Redis 的 `maxmemory-policy` 是 **`noeviction`** —— 内存满了会**拒绝写入并报错**，而不是静默淘汰。对主存储来说这**恰好是正确配置**：宁可写失败报错，也不静默丢会话。

#### 2.3 为什么 TTL 是 2h

会话本来就**有生命周期** —— 聊完就散了。用 Redis 的 `EXPIRE` 表达这件事，比自己写一套清理逻辑简单得多。

**语义细节**：TTL 是「**最后一次活动后 2h**」，不是「创建后 2h」。所以每次 `save` 都要重设 `ex`。聊得越久活得越久，这才对。

#### 2.4 为什么叫「主存储」不叫「缓存」

这不只是措辞。它决定了**故障时的行为**：

| 如果它是缓存 | 如果它是主存储 |
|---|---|
| Redis 挂了 → 降级，重算就好 | Redis 挂了 → **报错，不能降级** |

**为什么不能降级**：如果 Redis 挂了就静默降级成「每轮都是新会话」，用户看到的是**对话莫名失忆** —— 比直接报错难查得多。所以 `store.load` 抛异常时，让它抛出去（500），不要吞。

### 3. 三个关键设计决定（都反直觉）

#### 决定① `load` 返回「新建的」，**不返回 `None`**

```python
if raw is None:
    return AgentContext(conversation_id=..., project_id=...)   # ← 返回新建的
```

**目的**：**保持 P3 的语义不变**。

P3 的 `_load_context` 就是「没有就建一个」，所以路由层从来不用写 `if ctx is None`。现在换了存储，**这个契约必须保持不变** —— 否则路由层就得加判断，而路由层的设计原则是「**出现 `if` 多半是编排漏到了这一层**」（见 `agent.py` 文件头）。

> **这就是「只换存取、不碰业务」的具体含义**：调用方感觉不到存储换了。

#### 决定② `load` → 跑 → `save`，**不是每步都写 Redis**

```
ctx = await store.load(...)        # 读
_apply_focus(ctx, req.focus)       # 改（内存）
response = await run_turn(...)     # 改（内存，可能跑 25s）
await store.save(ctx)              # 写（一次）
```

**为什么**：`run_turn` 是**原地改 ctx 对象**的（`_remember` 往 `history` append、`budget.turns += 1`、`_navigate` 改 `focus_stack`）。如果每步都写 Redis，等于把一个内存操作拆成好几次网络往返，还可能写到一半失败留下**半截状态**。

**代价要认**：`run_turn` 中间可能跑 25s（两次 LLM），这期间第二个请求读到的是旧 Context。单用户连点两下会丢一次更新 —— **P4 接受，但这是决定不是疏忽**。

> ⚠️ `save` 放在 `run_turn` **之后**，意味着**异常时不写回**。这是有意的：炸掉的轮次不该把半截状态写进 Redis。
> 你可能问：`_apply_focus` 在 `run_turn` 之前已经改了 ctx，不保存岂不是丢了？**不丢** —— 焦点是从请求体传进来的，下一个请求会重新 `_apply_focus` 一遍。

#### 决定③ 反序列化失败 → **重建**，不是抛 500

```python
except ValidationError:
    logger.warning(...)
    return AgentContext(...)      # ← 当新会话
```

**这条要跟另一个「反序列化失败」划清界限**，别混：

| 位置 | 失败意味着 | 处置 | 为什么 |
|---|---|---|---|
| `java_client._post` | **和 Java 的契约**漂了 | **必须炸** | 吞掉会掩盖真 bug |
| `context_store.load` | **自己的内部存储**对不上 | **重建** | 代价只是「用户重开一句」 |

**它同时是「版本迁移策略」**：`AgentContext` 有个 `version` 字段，你以后改模型形状时，Redis 里那批老 Context 就都反序列化不了了。这时候：

- 抛出去 → 所有活跃会话在部署瞬间全部 500，直到 TTL 自然过期（最长 2h）
- **重建** → 老会话静默变成新会话，**而这正是设计 §2.4 决定③的既定语义**「丢了等于这次对话结束」

## 第二部分 · 开发思路（怎么做的）

### 4. 分层原则：只换「存取」，不碰「业务」

改动前后对比：

```python
# ── P3 ────────────────────────────────────
ctx = _load_context(req.project_id, conversation_id)     # 同步、读 dict
_apply_focus(ctx, req.focus)
response = await run_turn(ctx, req.message, java, llm)

# ── P4.1 ──────────────────────────────────
ctx = await store.load(req.project_id, conversation_id)  # 变：异步、读 Redis
_apply_focus(ctx, req.focus)                             # 不变
response = await run_turn(ctx, req.message, java, llm)   # 不变
await store.save(ctx)                                    # ★ 新增
```

**净改动只有 3 行。** `run_turn` 那 360 行一个字都没碰，`AgentContext` 模型也没碰。

> **为什么能这么干净**：因为 P3 就把边界画好了 —— `context.py` 当时就注明「Redis 持久化是 P4 的事，届时只加 `store/context_store.py`，**模型不动**」。今天只是兑现了那句话。

### 5. 依赖注入接缝（为什么 `get_context_store` 要做成 Depends）

看 `agent.py` 里那段注释的原话：

> 为什么要 Depends 而不是在路由里直接 `request.app.state.java_client`：那样测试就只能拿到真的 `JavaClient` 和真的 `LLMClient`，于是「低置信度会不会误调工具」这类分支根本没法测。

**store 遇到的是同一个问题**：如果不做接缝，`test_contract.py`（那个真打 app 的测试）就会**要求一个真 Redis 才能跑**。那样「本机没起 Redis」和「契约漂移了」在报告里长得一样 —— 而契约测试的红**只应该代表一件事：契约漂移了**。

所以 store 走和另外两个 client 完全一样的路：

```python
def get_context_store(request: Request) -> ContextStore:
    return request.app.state.context_store
```

## 第三部分 · 逐函数拆解

### 7. `ContextStore.__init__` —— 建连接（依赖注入 + 懒连接）

```python
def __init__(self, client: redis.asyncio.Redis | None = None) -> None:
    self._redis = client or redis.asyncio.from_url(
        settings.redis_url,
        db=settings.redis_db,
        password=settings.redis_password or None,
        decode_responses=True,
    )
```

**目的**：持有 Redis 连接池。

**三个设计点**：

1. **`client` 参数允许外部塞替身** —— 和 `JavaClient(base_url=None, token=None)` 同一个套路。这样测试可以注入假的，不必起真 Redis。
2. **`decode_responses=True` 必须设** —— 不设的话 `get()` 返回 `bytes`（`b'{"version":1,...}'`），JSON 解析会炸。而且**报的错是 JSON 解析错，不是类型错**，很难往回找。
3. **`_` 前缀**是 Python 的约定：**「这是私有的，别从外面碰」**。注意它**只是约定**，Python 不做强制（不像 Java 的 `private`）。

> ⚠️ **一个踩过的坑（血泪）**：参数最初叫 `redis`，**把 `redis` 模块名遮住了**，于是 `redis.asyncio` 取到的是那个 `None` 参数 → `AttributeError`，**服务根本起不来**。已改名 `client`。
>
> **教训**：**永远不要用你要调用的那个模块名当参数名。**

### 8. `ContextStore._key` —— 拼 Redis 的 key

```python
@staticmethod
def _key(project_id: int, conversation_id: str) -> str:
    return f"{_KEY_PREFIX}:{project_id}:{conversation_id}"
```

**目的**：key 的格式**只在一处定义**，避免 `load` / `save` / `evict` 三处各拼一遍、哪天改格式改漏一处。

**生成的结果**：`agent:ctx:2101954967776358402:c_f011cf1f...`

**三段各有用途**：

- `agent:ctx:` —— 命名空间，让 `evict` 能按前缀扫，也避免和别的 key 撞
- `{projectId}` —— **P3 就有的防御**：万一 Java 串了 projectId，两个项目的对话也不会互相污染
- `{conversationId}` —— 会话本身

### 9. `ContextStore.load` —— 读，自带三级兜底

```python
async def load(self, project_id: int, conversation_id: str) -> AgentContext:
    raw = await self._redis.get(self._key(project_id, conversation_id))
    if raw is None:
        logger.info(...)
        return AgentContext(conversation_id=conversation_id, project_id=project_id)
    try:
        return AgentContext.model_validate_json(raw)
    except ValidationError:
        logger.warning(...)
        return AgentContext(conversation_id=conversation_id, project_id=project_id)
```

**三级路径**：

| 情况 | 走哪条 | 结果 |
|---|---|---|
| Redis 里没有 | `raw is None` | 新建 |
| 有、能解析 | `try` | 还原 |
| 有、解析失败 | `except` | 新建（决定③） |

**为什么两个分支返回同一句话** —— 因为**对调用方来说它们是同一件事**：拿到一个可用的 Context。调用方不需要知道这是「新会话」还是「旧会话坏了」。

### 10. `ContextStore.save` —— 写，顺带续 TTL

```python
async def save(self, ctx: AgentContext) -> None:
    await self._redis.set(
        self._key(ctx.project_id, ctx.conversation_id),
        ctx.model_dump_json(by_alias=True),
        ex=settings.context_ttl_seconds,
    )
```

**两个细节**：

1. **`by_alias=True` 必须显式写死**。`CamelModel` 带 `alias_generator=to_camel` + `populate_by_name=True`，所以**蛇形、驼峰两种都能 round-trip** —— 正因为**都行**，你不写死就会**依赖 pydantic 的默认值**，那玩意儿容易记错、也可能随版本变。
2. **`ex=` 每次 save 都重设** → TTL 语义是「最后一次活动后 2h」（见设计 2.3）。

### 11. `ContextStore.evict_project` —— 按前缀批量删

```python
async def evict_project(self, project_id: int) -> int:
    pattern = f"{_KEY_PREFIX}:{project_id}:*"
    deleted = 0
    async for key in self._redis.scan_iter(match=pattern, count=100):
        await self._redis.delete(key)
        deleted += 1
    logger.info(...)
    return deleted
```

**⚠️ 必须用 `scan_iter`，绝不能用 `KEYS`**：

`KEYS` 会**阻塞整个 Redis 实例**（Redis 是单线程的！），连 db0 上 Java 的 overview 缓存都得等它扫完。`SCAN` 是游标式分批遍历，不阻塞。

**为什么返回 `deleted` 数量**：因为路由层现有的响应体是 `{"ok": True, "note": f"已清理 {n} 个会话 Context"}`。返回数量，**这个形状就不用改** —— P4.3 的 Java 网关也不用跟着改。

### 12. `get_context_store` —— 注入接缝

```python
def get_context_store(request: Request) -> ContextStore:
    return request.app.state.context_store
```

见第二部分 §5。**注意它是个普通函数**（不是 `async def`）—— 因为它只做一次属性读取，没有 IO。

### 13. `ask()` —— 编排（改了 3 处）

```python
async def ask(
    req: AskRequest,
    java: JavaClient = Depends(get_java_client),
    llm: LLMClient = Depends(get_llm_client),
    store: ContextStore = Depends(get_context_store),      # ★ 新增参数
) -> AgentResponse:
    conversation_id = req.conversation_id or _new_conversation_id()
    ctx = await store.load(req.project_id, conversation_id)  # ★ 变 await
    _apply_focus(ctx, req.focus)
    response = await run_turn(ctx, req.message, java, llm)
    await store.save(ctx)                                    # ★ 新增
    response.conversation_id = conversation_id
    return response
```

**`response.conversation_id = conversation_id` 这句为什么在这**（原来的注释）：`run_turn` 不知道 `conversation_id` 是新生成的还是回传的 —— 那是路由层的事，所以在这里补上。

### 14. `evict()` —— 改了实现，没改形状

```python
async def evict(req: EvictRequest, store: ContextStore = Depends(get_context_store)) -> dict:
    n = await store.evict_project(req.project_id)
    return {"ok": True, "note": f"已清理 {n} 个会话 Context"}
```

**响应形状与 P3 完全一致** —— 这是刻意的。

### 15. `health()` —— 诊断口（今天新增的）

```python
@app.get("/health")
def health() -> dict:
    return {
        "status": "ok",
        "javaBaseUrl": settings.java_base_url,
        "redisUrl": settings.redis_url,
        "redisDb": settings.redis_db,
        "llmConfigured": bool(settings.deepseek_api_key),
    }
```

**为什么加**：今天排查「服务起来了但连的是本机 Redis」时，**完全看不出它在连哪个地址**，绕了很多路。现在一眼就能确认。

**注意别泄露密码**：`redis_url` 里不含密码（密码在单独的 `redis_password` 字段），而 `llmConfigured` 只报「配没配」，不报内容。

### 16. `FakeContextStore` —— 测试替身

```python
class FakeContextStore:
    def __init__(self) -> None:
        self._data: dict[tuple[int, str], AgentContext] = {}

    async def load(self, project_id, conversation_id) -> AgentContext:
        key = (project_id, conversation_id)
        if key not in self._data:
            self._data[key] = AgentContext(conversation_id=conversation_id, project_id=project_id)
        return self._data[key]

    async def save(self, ctx: AgentContext) -> None:
        self._data[(ctx.project_id, ctx.conversation_id)] = ctx

    async def evict_project(self, project_id: int) -> int:
        doomed = [k for k in self._data if k[0] == project_id]
        for k in doomed:
            del self._data[k]
        return len(doomed)
```

**目的**：让 `test_contract` 不依赖真 Redis（本质就是 P3 那个内存 dict 的复活，只不过只用于测试）。

**为什么叫 fake 不叫 mock**（项目自己的约定）：这些是**有真实行为的手写替身**，不是「记录调用参数」的桩。

**语义必须和真 store 对齐**：`load` 取不到就返回新建的，**不返回 `None`** —— 见决定①。

### 17. `config.py` 的修复 —— `.env` 用绝对路径

```python
_ENV_FILE = Path(__file__).resolve().parent.parent / ".env"
```

**修的是什么**：`env_file=".env"` 是**相对路径，相对于「启动时的工作目录」**。从别处（比如仓库根）启动服务就找不到它，于是：

- Redis 连成本机 `localhost:6379`
- **`DEEPSEEK_API_KEY` 变成空串**
- **而且不报任何错**

从**代码文件**定位就没这个问题：`__file__` 是当前文件的路径，`.parent` 是 `app/`，`.parent.parent` 是 `agent-service/`。

### 18. `tests/test_app_smoke.py` —— 补一个洞

```python
def test_app_boots_and_health_ok() -> None:
    with TestClient(app) as c:
        resp = c.get("/health")
    assert resp.status_code == 200
    assert resp.json()["status"] == "ok"
```

**为什么需要它**：今天那个「参数遮住模块名 → 服务起不来」的 bug，**43 个测试全绿却没发现**：

- 离线那批（guard/intent/loop）**根本不碰 app**
- `test_contract` 在 `require_java` 那步就 skip 了 → `TestClient(app)` 从没进去过 → **lifespan 从没跑过**

也就是说：**「app 能不能启动」这件事当时没有任何测试在看。** 这条测试只干一件事：把 lifespan 跑一遍。**不需要 Java，也不需要 Redis**（`from_url` 是懒连接，不 get/set 就不拨号）。

## 第四部分 · 调用关系（谁和谁一起完成了什么）

### 19. 一次 `/ask` 的完整链路

```
HTTP POST /internal/agent/ask
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│ dependencies=[Depends(require_internal_token)]           │  ← 先鉴权
│   共享密钥校验，不过直接 401，进不到下面                    │
└─────────────────────────────────────────────────────────┘
        │
        ▼
   FastAPI 解析参数，依次执行三个 Depends：
     ├── get_java_client(request)  → app.state.java_client
     ├── get_llm_client(request)   → app.state.llm_client
     └── get_context_store(request)→ app.state.context_store   ★
        │
        ▼
   conversation_id = req.conversation_id or _new_conversation_id()
        │                              └── uuid.uuid4().hex[:16]
        ▼
   ctx = await store.load(pid, cid)                            ★
        │      └── _key() 拼 key → redis.get → model_validate_json
        ▼
   _apply_focus(ctx, req.focus)      ← 纯内存，焦点变化时旧的压栈
        │
        ▼
   response = await run_turn(ctx, req.message, java, llm)
        │      ├── core/intent  判意图
        │      ├── tools/registry 选工具 → java_client 打 Java
        │      ├── core/explain LLM 讲解
        │      └── core/guard   幻觉拦截
        ▼
   await store.save(ctx)                                       ★
        │      └── _key() 拼 key → model_dump_json → redis.set(ex=7200)
        ▼
   response.conversation_id = conversation_id
        │
        ▼
     返回 AgentResponse
```

### 20. 「谁和谁共同完成了什么」对照表

| 目的 | 由哪几个函数**共同**完成 |
|---|---|
| **会话状态跨进程共享** | `ContextStore.__init__`（建连接）+ `_key`（定寻址）+ `load`/`save`（读写）+ `main.py` lifespan（持有生命周期） |
| **路由层保持无分支** | `load` 返回新建而非 `None`（决定①）+ `AgentContext` 模型自带默认值 |
| **TTL 是「最后活动后 2h」** | `save` 的 `ex=` + `settings.context_ttl_seconds` |
| **删项目能清干净** | `evict_project`（scan_iter 前缀删）+ `evict()` 路由（透传数量）+ key 里带 projectId |
| **测试不依赖真 Redis** | `get_context_store`（接缝）+ `FakeContextStore`（替身）+ `test_contract` 的 `dependency_overrides` |
| **配置从哪启动都对** | `config.py` 的 `_ENV_FILE` + `Path(__file__).resolve()` |
| **故障可诊断** | `health()` 报出生效配置 + `ContextStore.__init__` 用 `settings.*` 而非硬编码 |

### 21. 三层「兜底」是三个不同的东西，别混

| 层 | 位置 | 触发条件 | 处置 |
|---|---|---|---|
| **配置层** | `config.py` | 找不到 `.env` | 回落默认值（**已用绝对路径堵住**） |
| **存储层** | `store.load` | key 不在 / JSON 坏了 | 新建 Context（决定①③） |
| **业务层** | `loop.run_turn` | LLM 挂了 / Java 连不上 | 降级回答，不 500（C2） |

## 第五部分 · Python 语法讲堂（对照 Java）

> 只讲**这次真正用到的**语法，且都对着 Java 讲。

### 22. 导入

```python
import logging                      # 整个模块
import redis.asyncio                # 子模块
from pathlib import Path            # 只要其中一个东西
from app.config import settings     # 从自己的包
```

**对应 Java**：`import java.util.List;` 大致相当于 `from app.config import settings`（只取一个名字）；`import logging` 相当于用一个类名来限定。

**⚠️ 一个容易踩的**：`import redis.asyncio` 之后才能写 `redis.asyncio.from_url(...)`。只写 `import redis` 拿不到 `.asyncio`。这就是今天那个 bug 的一半原因。

### 23. 类型注解（**只是给人和 IDE 看的，运行时不强制**）

```python
def _key(project_id: int, conversation_id: str) -> str:
    ...
```

**对应 Java**：`String _key(int projectId, String conversationId)`

**⚠️ 关键区别**：Python 的注解**不做类型检查**！传错类型照样跑（直到出错那行才炸）。所以它更像 Java 的注解（`@Nullable`）而不是泛型约束。

```python
client: redis.asyncio.Redis | None = None
```

**对应 Java**：`Redis client = null;`，`| None` ≈ `Optional<Redis>`。

```python
dict[tuple[int, str], AgentContext]
```

**对应 Java**：`Map<Map.Entry<Integer,String>, AgentContext>`，或更接近 `Map<Tuple<Integer,String>, AgentContext>`。`tuple[int, str]` 是「固定两个元素、类型分别为 int 和 str」。

**`-> None`** ≈ Java 的 `void`。

### 24. `async def` / `await`（**这是最大的思维差异**）

```python
async def load(self, project_id: int, conversation_id: str) -> AgentContext:
    raw = await self._redis.get(self._key(project_id, conversation_id))
```

**对应 Java**：不是 `synchronized`，也不是线程。Python 的协程是**单线程内的事件循环**：

| | Java 传统 | Python asyncio |
|---|---|---|
| 并发手段 | 多线程 / 线程池 | 单线程 + 事件循环 |
| 阻塞调用 | 线程挂起，OS 调度 | **`await` 时主动让出**，去跑别的协程 |
| 写法 | 同步写 | `async def` 定义，`await` 调用 |

**怎么读**：

- `async def` = 「这是个协程函数，调用它**不会立刻执行**，返回一个协程对象」
- `await X` = 「**在这里等 X 完成，等的过程中把 CPU 让给别人**」
- **只有 `async def` 里面才能 `await`**

**为什么要这样**：Agent 一轮要等 LLM 25s、等 Java 8s —— 全是 IO 等待。用线程的话，每个请求一个线程，几千个请求就爆了；用事件循环，一个线程能同时挂起几千个等待中的请求。

**对应你 P3 已经见过的**：`run_turn` 是 `async def`，`java_client._post` 用 `httpx.AsyncClient` —— 全是这个模型。

> ⚠️ **所以 `_load_context` 改成 `store.load` 之后必须加 `await`** —— 不加的话你拿到的是「协程对象」而不是 Context，后面全乱。

### 25. `@staticmethod` 装饰器

```python
@staticmethod
def _key(project_id: int, conversation_id: str) -> str:
    return f"..."
```

**对应 Java**：`static String _key(...)` —— 不需要实例就能调，**没有 `self`**。

**装饰器（`@xxx`）**对应 Java 的**注解**，但**作用完全不同**：Java 注解靠框架反射读；Python 装饰器是**真的在运行时把函数换掉**（`@staticmethod` 把函数包成静态方法）。

### 26. `@router.post(...)` —— FastAPI 的路由注册

```python
@router.post("/ask", response_model=AgentResponse, dependencies=[Depends(require_internal_token)])
async def ask(...) -> AgentResponse:
```

**对应 Java**：完全是 `@PostMapping("/ask")` + `@PreAuthorize` 的合体。

- `"/ask"` + 路由前缀 `/internal/agent` → 完整路径 `/internal/agent/ask`
- `response_model=AgentResponse` → 返回体自动校验 + 生成 Swagger 文档（≈ Spring 的 `@ResponseBody` + 校验）
- `dependencies=[...]` → **进函数之前先跑这个**，不过就 401（≈ `@PreAuthorize`）

### 27. `Depends(...)` —— FastAPI 的依赖注入

```python
def get_java_client(request: Request) -> JavaClient:
    return request.app.state.java_client

@router.post("/ask")
async def ask(java: JavaClient = Depends(get_java_client), ...):
```

**对应 Java**：**非常像** Spring 的构造器注入：

| Spring | FastAPI |
|---|---|
| `@Bean JavaClient javaClient()` | `def get_java_client(...)` |
| 构造器参数自动注入 | 参数写 `= Depends(get_java_client)` |
| `@MockBean` 替换 | `app.dependency_overrides[...] = lambda: fake` |

**关键点**：**测试能用一个 dict 把真的换成假的**（`dependency_overrides`），这就是它存在的全部意义（第二部分 §5）。

**`request: Request` 是什么**：FastAPI 会自动把当前 HTTP 请求对象传进来。`request.app.state.xxx` 就是「从全局储物盒里取东西」—— `app.state` 是在 `lifespan` 里塞东西的地方。

### 28. f-string

```python
f"{_KEY_PREFIX}:{project_id}:{conversation_id}"
f"c_{uuid.uuid4().hex[:16]}"
f"已清理 {n} 个会话 Context"
```

**对应 Java**：`String.format("%s:%d:%s", prefix, pid, cid)`，或 Java 15+ 的 `"%s:%d".formatted(...)`。

**规则**：字符串前面加 `f`，里面 `{表达式}` 会被求值。比 Java 的 `%s` 好记（不用管顺序和类型符）。

**`uuid.uuid4().hex[:16]` 语法拆解**：

- `uuid.uuid4()` → 生成一个随机 UUID 对象
- `.hex` → 取它的十六进制字符串（32 个字符）
- `[:16]` → **切片**，取前 16 个字符。Python 切片 `s[a:b]` 对应 Java 的 `s.substring(a, b)`

### 29. 默认参数 + `or` 短路当默认值

```python
def __init__(self, client: redis.asyncio.Redis | None = None) -> None:
    self._redis = client or redis.asyncio.from_url(...)
```

**`client or X` 是什么意思**：Python 的 `or` **返回的是值，不是布尔**！

- 如果 `client` 是「真值」（非 `None`、非空、非 0）→ 返回 `client`
- 否则 → 返回 `X`

**对应 Java**：`this.redis = client != null ? client : createDefault();`

**⚠️ 陷阱**：因为空字符串、`0`、`[]` 都是「假值」，如果 `client` 有可能是 `0` 或 `""`，`or` 会误判。这里 `client` 只可能是对象或 `None`，安全。

### 30. 关键字参数

```python
redis.asyncio.from_url(
    settings.redis_url,
    db=settings.redis_db,
    decode_responses=True,
)
```

**对应 Java**：Java 没有这个。Python 允许**按名字传参**，调用点因此自解释（不用数第几个参数）。

**规则**：`名字=值`。所以 `ctx.model_dump_json(by_alias=True)` 一眼能看出在设什么。

### 31. try / except / raise ... from

```python
try:
    return AgentContext.model_validate_json(raw)
except ValidationError:
    return AgentContext(...)
```

**对应 Java**：`try / catch (ValidationError e)`。**但注意 Python 不写异常类型变量**（不需要 `e`，除非你要用）。

```python
raise LLMTransportError(f"...") from e
```

**`from e` 对应 Java 的**：`throw new XxxException("...", e)`（**保留原因链**，Java 里是构造器第二个参数）。

### 32. `async for` —— 异步迭代

```python
async for key in self._redis.scan_iter(match=pattern, count=100):
    await self._redis.delete(key)
```

**对应 Java**：`for (String key : iterable)`，但**每次取下一个元素是异步的**（因为要跟 Redis 要下一批）。

`scan_iter` 内部就是「拿一批 → yield → 再拿一批」，所以是 `async for`。

### 33. `self` 与类

```python
class ContextStore:
    def __init__(self, client=None) -> None:
        self._redis = client or ...
```

**对应 Java**：`self` **就是 `this`**，但**必须显式写**（Java 里可以省略 `this.`）。所以：

| Java | Python |
|---|---|
| `this.redis` | `self._redis` |
| `private final Redis redis;` | `self._redis = ...`（`__init__` 里赋） |
| 构造器 `public Foo() {}` | `def __init__(self) {}` |

**`__init__` 就是构造器**（双下划线开头/结尾的叫「魔术方法」，Python 靠它们实现运算符和协议）。

### 34. 模块级 vs 类内

```python
logger = logging.getLogger(__name__)     # 模块级
_KEY_PREFIX = "agent:ctx"                # 模块级常量（大写是约定）

class ContextStore:
    @staticmethod
    def _key(...): ...
```

**对应 Java**：模块级 ≈ Java 的 `static` 字段/方法（在类外面）。**Python 不需要把所有东西塞进类里** —— 这是个大差别。

**`__name__`** ≈ Java 里拿当前类的全名（`ContextStore.class.getName()`），用来自动给 logger 命名。

### 35. 列表推导 + 其他零碎

```python
doomed = [k for k in self._data if k[0] == project_id]
```

**对应 Java**：`stream().filter(k -> k.getKey() == pid).collect(toList())`

**规则**：`[表达式 for 元素 in 集合 if 条件]`。比 Java 的 stream 短很多。

```python
sys.exit(1)              # ≈ System.exit(1)，退出进程
sys.argv[1]              # ≈ args[0]（argv[0] 是脚本名，所以下标差 1）
```

```python
with TestClient(app) as c:
    ...
```

**对应 Java**：`try (var c = new TestClient(app)) { ... }`（try-with-resources）。`as c` 相当于给资源起变量名。

```python
bool(settings.deepseek_api_key)
```

**对应 Java**：`!key.isEmpty()` 更严格的版本 —— 把任意值转成布尔（空串 → `False`）。

```python
if __name__ == "__main__":
    ...
```

**对应 Java**：`public static void main(String[] args)` 的守卫。意思是「**只有直接运行这个文件时才执行**，被 import 时不执行」。

### 36. 两个「协议/模型」概念（P3 就用着，顺带说清）

**`Protocol`（`llm.py` 里的 `Completer`）**

```python
class Completer(Protocol):
    async def complete(self, messages, *, json_mode=False) -> LLMResult: ...
```

**对应 Java**：**接口**。区别是 Python 用的是**结构类型**（duck typing）—— 只要你的类**有**这个方法就算实现了，不需要 `implements Completer`。

**为什么要有它**：`run_turn` 只依赖 `Completer` 这个最小接口，于是测试能塞 `FakeLLM` 进去，不必起真 LLM。

**`pydantic.BaseModel`（`CamelModel`）**

```python
class AskRequest(CamelModel):
    project_id: int
    message: str
    conversation_id: str | None = None
```

**对应 Java**：`record AskRequest(int projectId, String message, String conversationId)` **+ Bean Validation + Jackson 反序列化**，三合一。

- 声明字段 + 类型 → 自动校验
- `CamelModel` 的 `alias_generator=to_camel` → **JSON 里自动是驼峰，Python 里写蛇形**（这就是 `BASE.py` 那段注释说的）
- `model_validate_json(raw)` ≈ `objectMapper.readValue(raw, AgentContext.class)`
- `model_dump_json()` ≈ `objectMapper.writeValueAsString(ctx)`

**`model_config = SettingsConfigDict(env_file=..., env_file_encoding="utf-8")`**：类级别的配置（≈ Java 类上的注解 `@PropertySource`）。

## 第六部分 · 今天的教训（值得单独记）

| # | 教训 | 具体 |
|---|---|---|
| 1 | **别用你要调的模块名当参数名** | `def __init__(self, redis=None)` 遮住了 `redis` 模块 → 服务起不来 |
| 2 | **`env_file=".env"` 是相对 cwd 的** | 从别处启动就静默读不到 → 所有配置回落默认值，不报错 |
| 3 | **`--reload` 不盯 `.env` / `.yml`** | 只盯 `.py`。改了配置必须手动重启 |
| 4 | **测试全绿 ≠ 服务能起** | 43 个测试没覆盖 lifespan，漏掉了「服务起不来」 |
| 5 | **降级路径的返回值可能和你以为的不一样** | `_tool_down` 不返回 `suggestions`，验收脚本的判据因此假失败 |
| 6 | **相对路径的默认值是「静默」的** | 它不报错，只是用了别的值 —— 这类 bug 最难查 |

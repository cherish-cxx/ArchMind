> 主题：把 `analyze` 从「同步阻塞请求线程」改造成「提交即返回 taskId → 后台线程池执行 → 前端轮询进度」的异步任务系统

## 一、今天的目标：为什么要把 analyze 改成异步

**改造前**（9月9 留下的坑位）：

```
POST /api/project/{id}/analyze → 【Tomcat 请求线程被占住】→ 读 pom/README → 调 LLM 5~30 秒 → 返回概况
```

三个问题：

1. **请求线程被长任务占住**。Tomcat 默认 200 个请求线程，一个分析占一个。几个用户同时分析，线程被吃光 → **其他人连登录都进不来**。
2. **用户全程白屏**。前端只有一个转圈的等待，不知道在干什么、还要多久。
3. **无法重跑 / 看不到失败原因**。

**改造后**：

```
POST /api/project/{id}/analyze → 建任务行 + 投递线程池 → 立即返回 {taskId, status:PENDING}
                                   ↓ 【后台 analysis-1 线程】
                                   SCAN → AST → OVERVIEW，边跑边写进度
前端：GET /api/task/{taskId} 每 1~2 秒轮询一次，直到 SUCCESS → 再拉 overview
```

> **关键认识**：异步 ≠ 简单地把活挪到后台。如果把活挪走但不写进度，用户盯着一个永远 0% 的进度条，**体验比同步还差**（同步至少界面会转圈）。所以「异步」和「进度上报」是同一件事的两面，必须一起做。

## 二、异步的逻辑结构（四层）

```
Controller（同步）         ProjectAnalysisController（提交） / TaskController（查询）
      ↓
TaskService（同步）        状态机：建任务、写状态、查询。唯一往 task 表写状态的地方
      ↓ 投递
AnalysisTaskExecutor      @Async("analysisExecutor")：只管「切阶段 / 驱动 / 处理成败 / 放锁」
      ↓ 驱动
AnalysisPipelineService   三个阶段的业务算法：scanStage / astStage / overviewStage（同步、可单测）
```

职责边界（为什么要拆四层，而不是塞一个类）：

| 层           | 负责              | 不负责      |
| ----------- | --------------- | -------- |
| Controller  | HTTP 出入参、归属校验   | 任何业务     |
| TaskService | 任务生命周期状态、锁、查询   | 分析算法     |
| Executor    | 什么时候调哪个阶段、出错怎么办 | 具体怎么算    |
| Pipeline    | 每个阶段具体怎么算       | 状态、线程、成败 |

类比：Executor 是**项目经理**（排期、处理突发），Pipeline 是**工人**（真干活），TaskService 是**记工分的人**。三者混在一个类里，就是「一个人又当经理又当工人又记账」，又长又不能单测。

## 三、阶段展示与前端交互

### 阶段与进度区间（`AnalysisStage`）

| 阶段 | 中文 | 区间 | 说明 |
| --- | --- | --- | --- |
| `SCAN` | 文件扫描 | 0 → 15 | P1 中上传时已完成，此处占位 |
| `AST` | AST 提取 | 15 → 65 | P1 第二刀实现（JavaParser + Neo4j） |
| `OVERVIEW` | 概况生成 | 65 → 100 | 读 pom/README → 调 LLM |

把百分比写进枚举（`progressAt(阶段内%) → 全局%`），将来加「领域拆分」阶段只改一处，执行器和前端都不用动。

### 前端交互时序

```
① POST /api/project/1/analyze?force=false
   ◄── { taskId: 123, status: "PENDING", progress: 0 }     ← 毫秒级返回

② GET /api/task/123   （每 1~2 秒一次，直到 status 进终态）
   ◄── { status:"RUNNING", progress:40, currentStage:"AST", stageLabel:"AST 提取" }

③ status === "SUCCESS" → GET /api/project/1/overview        ← 拿最终概况
```

### 接口契约变化（⚠️ 前端要改）

| 接口 | 改前 | 改后 |
| --- | --- | --- |
| `POST /{id}/analyze` | 返回 `ProjectOverviewResponse`（阻塞等结果） | 返回 `TaskResponse`（立即返回 taskId） |
| `GET /api/task/{taskId}` | — | 新增，查进度 |
| `GET /api/project/{id}/tasks/latest` | — | 新增，前端刷新/换页后找回在跑的任务（否则进度条丢失） |
| `GET /api/project/{id}/overview` | 不变 | 不变（终态后拉结果） |

**快路径**：`force=false` 且已有概况时，`submitAnalysis` **不建任务、不占线程**，直接返回一个 `status=SUCCESS` 的合成响应（`taskId=null`）。

## 四、Redis 高频刷新：进度写入为什么分两路

| 方法 | 写到哪 | 频率 | 内容 |
| --- | --- | --- | --- |
| `enterStage(taskId, stage)` | **MySQL** | 全程 3 次 | `current_stage` + `progress=阶段起点` |
| `reportProgress(taskId, stage, pct)` | **Redis** | 可能几百次 | `"40\|AST"`（TTL 1h） |

**为什么不能都写 DB**：AST 阶段处理 500 个 java 文件，若每个文件 `UPDATE task SET progress=...` → 500 次写库 + 锁行，数据库被打爆，**为了看进度把系统拖垮**。
**为什么不能都写 Redis**：Redis 不持久，重启就丢，且带 TTL。

所以：**高频进 Redis（便宜、丢了无所谓，下个阶段切换会补写）；阶段切换进 DB（持久）。查询时合并——DB 读权威状态，Redis 覆盖更新的数字**（`overlayLiveProgress`）。

一条经验：**「高频写同一个值」的场景，永远不要直接打 DB**，先在内存/缓存里攒着，到关键节点再落库。

## 五、循环依赖：TaskServiceImpl ↔ AnalysisTaskExecutor

```
TaskServiceImpl ──①投递任务 executor.run()──> AnalysisTaskExecutor
      ^                                              │
      └────────②写状态 taskService.markXxx()──────────┘
```

两边**确实互相需要**（提交方要能点火，执行方要能写黑板），是天然的环。**Spring Boot 2.6+ 默认 `allow-circular-references=false`，启动直接抛 `BeanCurrentlyInCreationException`**。

**今天用 `@Lazy` 破环**：注入的不是真身而是代理，推迟到第一次 `executor.run()` 时才创建真身，启动期就没环了。

**遗留问题**：`@Lazy` 是「绕过」不是「消除」，环还在，将来排查代理套代理（`@Async` 也是代理）会痛苦。**建议第二刀之后重构成无环**：

```
TaskServiceImpl ──> AnalysisTaskExecutor ──> TaskStateMachine   ✅ 单向，无环
       └──────────────────────────────────> TaskStateMachine
```

即把 6 个状态转移方法抽成独立的 `TaskStateMachine` bean，Executor 只依赖它，不再依赖 TaskService。

## 六、三级缓存：和这个问题是什么关系（概念澄清）

**三级缓存就是 Spring 自己「解决循环依赖」的机制**，即 `DefaultSingletonBeanRegistry` 里的三个 Map：

| 级别 | 字段 | 存什么 |
| --- | --- | --- |
| 一级 | `singletonObjects` | 成品 bean |
| 二级 | `earlySingletonObjects` | 提前暴露的早期引用 |
| 三级 | `singletonFactories` | `ObjectFactory`，生产早期引用（必要时生成 AOP 代理） |

机制：A 实例化后把工厂放进三级缓存 → 填充属性发现需要 B → 创建 B → B 需要 A 时从三级缓存拿到 A 的早期引用注入 → 环被打断。

**为什么救不了我们这种情况**：三级缓存能提前暴露的前提是 **`new A()` 已经执行完**（A 这个对象已在内存，只是没填属性）。而我们是**构造器注入**——`new TaskServiceImpl(..., executor)` 里 executor 还没造出来，TaskServiceImpl 连空壳都不存在，**没有任何东西可以提前暴露**。构造器注入的循环依赖，Spring 文档明确说不支持。

**第二层原因**：即使改成 setter/字段注入（三级缓存本来能处理的那种），Boot 2.6 起默认关闭了循环引用，Spring 一检测到就抛异常，根本不走三级缓存那套。

**与 `@Lazy` 的区别**：

| | 三级缓存 | `@Lazy` |
| --- | --- | --- |
| 机制 | 容器内部「先发半成品」 | 注入点放代理，推迟创建真身 |
| 适用范围 | 仅 setter / 字段注入 | 与注入方式无关，构造器也管用 |
| 现在默认可用吗 | ❌（被开关关掉） | ✅ |

> 面试向：被问「Spring 怎么解决循环依赖」→ ①讲三级缓存流程（能解释二级/三级为何分开是加分：三级为延迟生成 AOP 代理，二级为避免重复生成）②补边界：仅 setter/字段注入、单例、且不走特殊后处理器；构造器注入不行 ③补现状：Boot 2.6+ 默认关闭，更推荐**用设计避免循环依赖而非靠机制兜底**——正好接上本项目的 `@Lazy` 经历。
> 顺带纠正误区：三级缓存**本不是为循环依赖设计的**，它原本是给 AOP 提前暴露代理用的，解循环只是副产品。

## 七、第一次写异步踩的坑（清单，供以后复用）

| # | 坑 | 不处理的后果 | 解法 |
| --- | --- | --- | --- |
| 1 | **SecurityContext 传不到异步线程** | ThreadLocal 在新线程是空的 → `getCurrentUserId()` 返回 null → 归属校验被跳过 → **越权** | 在**请求线程**里 `checkProject` + 取 userId，**显式当参数传进**异步方法 |
| 2 | **`@Async` 自调用失效** | 同类内部 `this.xxx()` 绕过代理 → 变同步，白写 | 异步方法放独立 bean，由别的 bean 注入调用 |
| 3 | **默认线程池不可控** | `SimpleAsyncTaskExecutor` 每任务新建线程、无上限 → 拖死机器 | 自定义 `ThreadPoolTaskExecutor`（core 4 / max 8 / queue 100 / CallerRunsPolicy） |
| 4 | **并发重复分析** | 两个请求同时通过「没分析过」检查 → **两次调 LLM** + 抢写同一批 overview | Redis `SETNX` 抢锁（TTL 300s），抢不到直接拒绝 |
| 5 | **异步异常没人接** | 异常抛回线程池只打日志 → 任务**永远卡 RUNNING** | `try/catch(Throwable)` 全包，catch 里 `markFailed` |
| 6 | **落库与投递顺序** | 插入在未提交事务里，异步线程查不到这条任务 | 不套大事务：先 `insert`（提交）再投递 |
| 7 | **重启僵尸任务** | 内存队列消失，task 表还写着 RUNNING | `@PostConstruct` 把遗留 PENDING/RUNNING 标 FAILED |

另外两个实现细节：

- **`TaskServiceImpl` ↔ `AnalysisTaskExecutor` 循环依赖** → 见第五节，暂时 `@Lazy`。
- **`Task` 实体字段**原来写成 `current_stage` 下划线命名，改回 `currentStage`（MP 的 `mapUnderscoreToCamelCase` 默认 true，驼峰 ↔ 下划线自动映射）。

## 八、任务状态机

```
PENDING ──→ RUNNING ──→ SUCCESS
                     ├→ PARTIAL   （P1 未用，留给多阶段失败重试）
                     └→ FAILED
```

- **为什么要状态机**：异步方法没有返回值，结果**只能通过 task 表这块「黑板」传递**。前端轮询看的就是它——所以状态必须集中在一处按规矩写，不能谁都来改。
- **谁写**：只有 `TaskServiceImpl`（唯一真相来源）。`markRunning / enterStage / reportProgress / markSuccess / markFailed / releaseLock`。
- **`analysis_status` 的写权已收归 TaskService**（`markSuccess → COMPLETED`、`markFailed → FAILED`），`ProjectOverviewServiceImpl.generateOverview` 不再改状态，避免两处写漂移。

## 十、今天学到什么（可讲给面试官）

1. **异步的完整闭环**：提交即返回 → 状态机 → 线程池 → 进度上报 → 前端轮询。不是「开个线程」那么简单。
2. **为什么进度要分 Redis / DB 两路写**：高频写不打库，关键节点才落库。
3. **循环依赖**：构造器注入的环三级缓存救不了，要么 `@Lazy`（绕过）、要么抽独立 bean（消除）。**能把「三级缓存不适用于构造器注入」讲清楚，比背流程更能拿分**。
4. **`@Async` 的四个必踩坑**：SecurityContext 丢失、自调用失效、线程池要自定义、异常必须自己吞。

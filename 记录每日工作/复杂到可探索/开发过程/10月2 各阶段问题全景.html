P1 · Java 工具 API

9/21
5 个 /internal/tools/* 接口 + 2 个新算法
★变长 Cypher 表达不了「中途换关系类型」
扇出要走 CALLS → IMPLEMENTS → 再回 CALLS → 弃用变长 Cypher，改 Java 侧逐层 BFS
撞接口是常态 → 反向扇出把死路变分支点
沿 IMPLEMENTS 找到实现类，再按签名匹配。且扇出不计 depth——计了的话 depth≤2 永远穿不过接口
method-body 的 startLine 从第一个注解算起
@GlobalTransactional 这类会被切进去，javadoc 不会
接口方法是单行，切片只能拿到签名
→ 顺 IMPLEMENTS + signature 自动跳实现类，用 resolvedFrom 标明原 uid
⚠UP 语义不一致
class-relations 的 UP 只看直接 CALLS 边；call-chain 的 UP 带反向扇出 → 同一个问题两个数字
⚠classes 默认 limit=40 有排序偏差
返回的 40 条全是老单体包，trade 一个都没有 → 这条「让 LLM 在清单里选」的兜底基本失效
设计写「maxNodes 硬上限 40」是错的
真值是 MAX_NODES_HARD = 200；Java 是 clamp 不是拒绝 → 预算必须 Python 显式传
mvnw spring-boot:run 会 fork 出独立 JVM
停掉 Maven 进程，java 不会跟着退 → 得 taskkill 另找 PID

P2 · Python 契约 + java_client

9/25 – 9/30
给两边定下不会漂移的类型边界
★契约漂移：文档只写了信封字段名
5 个工具的 data 载荷形状只存在于 Java DTO 里 → 契约必须照代码抄，不能照文档抄
★参数静默降级（最阴的一个）
strArg/intArg 找不到 key 就吃 fallback，不抛异常不记日志 → HTTP 200、结果悄悄不对
数字必须是 JSON number，不能是字符串
发 "2" 同样落回默认值 2 —— 碰巧和想传的一样，所以更难发现（传 "1" 才暴露）
Jackson 没配 NON_NULL，显式 null 会发出来
Pydantic 的 = 默认值 对「键不存在」生效、对显式 null 无效 → 可为空字段必须写 | None
graphRev=0 不是错误
0 = 从未落图（或图建于版本号机制之前）→ 别当异常，也别拿它判断「图能不能用」
gaps 只在 DOWN 方向产生
UP 的空结果是合法的，不是「断链」
测试起点选错会永远绿
IOrderService 在 depth=1/2 下结果完全相同 → 用它测「参数有没有生效」跑一万遍也是绿；换 OrderController 才分得出 3 vs 8 个节点
系统代理劫持 localhost
httpx 从注册表读代理 → 连 localhost:8080 都被丢给 7897 → 超时/502，而同一台机器 curl 却正常。须 trust_env=False
curl 传中文 → 400 parsing the body
命令行参数按本地代码页转码，产出的不是合法 UTF-8 → 须 --data-binary @file
契约测试该 skip 不该 fail
红只应该代表一件事：契约漂移了。环境问题不该制造假警报

P3 · Agent 循环

10/1
Intent 判定 + LLM 讲解 + 四道拦截
★json_object 模式有隐藏前置条件
prompt 里必须出现 "json" 字样，否则 400 —— 而且报的错指向别处，极难查。专门写了条测试钉住它
★citations ⊆ evidence 的保证被削弱
P2 是「先选 citations 再拼 message」，结构上不可能引用没出处的东西；message 变成自由文本后拦不住了 → 只剩 prompt + 事后剔除
想扫 message 里的类名 → 放弃
LLM 写简单名、evidence 是全限定名，必然大量误报。天天误报的检查等于没有检查
LLM 和 Java 都不确定性，分支根本测不了
→ 造 FakeLLM / FakeJava。FakeLLM 的剧本元素还能是异常实例，一轮里两层降级一起覆盖
路由直接从 app.state 拿 client，测试注不进去
→ 改成 Depends，这才有 dependency_overrides。这是那层单测能存在的前提
⚠UP 路由 bug 在真实问答里暴露
点中实现类问「谁调用了它」→ 答「只有它自己」；真实答案是 3 个类。问接口两者一致，问实现类才岔开
NAVIGATE 的「不调 LLM」做不到
要判出它是 NAVIGATE，就得先调 LLM #1 → 真做到零 LLM 需要前端直接声明意图
超时预算自相矛盾
设计写「Java 代理 Python 8s」，但 Python 一轮要调两次 LLM → LLM 一慢，网关就先掐断
一轮只查一次图
ReAct 多步规划（LLM 决定下一步调什么）没做，接缝留在 loop 里但未接
Halt 后自检：留下的债
deploy/.env 缺 INTERNAL_TOKEN · DEEPSEEK_API_KEY 存两处 · 上传后未清旧概况 · 删项目未清 task 行

⚠ 标的是至今没解决的遗留，目前有 6 条： UP 语义不一致 · classes 排序偏差 · NAVIGATE 零 LLM · 超时预算矛盾 · ReAct 未做 · 一批运维小债。
一个规律：每阶段的坑可以归成三类 —— 图谱类（AST 表达能力的边界）、契约类（静默失败，最难查）、环境类（能骗过 curl 的假象）。 三类里契约类最危险，因为它不报错。

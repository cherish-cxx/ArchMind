# 10月25 画布 v2（R3）：方案讨论与前三项落地

> 状态：关系编码、节点卡片、按需描述三项已实现；布局与折叠未开始。
> 改动分布在两个仓库：`ArchMind`（Java + Python + 文档）与 `ArchMind-react`（前端）。

## 0. 一句话总结

今天先把 R3 的方案吵清楚了，然后落地了前三项：**四种关系一眼能分、节点默认只显示名字、鼠标停上去看详情、没有描述的类自动补一句介绍**。布局分组、装箱、多画布这些只定了方案，还没写。

## 1. 讨论过程：一开始的想法，后来改了哪些

一开始列了五件事：关系视觉编码、节点卡片、代码抽屉、按包聚块布局、200 节点折叠。讨论中纠正了几个事实，方案也跟着变了：

1. **“所有类都应该有描述”不成立。**
   去查了落图代码：建图阶段根本没写 `description`，只有分析完成后的一段逻辑给**关联度前 20 名**写了描述。所以数据库里绝大多数类是没有描述的，不是“字段存在但为空”。

2. **“加个独立字段区分核心/次核心”被撤回了。**
   核心类就是度数前 20，读取时按同一套规则重算就能知道，不需要落库。重分析会清空重建整张图，描述也会跟着没了，所以也不需要版本号或 hash 去失效。

3. **“只对实现的类做描述”基本同意，但留了一个例外。**
   接口只是契约，行为在实现类里，所以批量描述只覆盖“非抽象的具体类”。但**用户当前选中的中心类必须描述**，哪怕是接口——否则点开一个 Service 接口，最中间的卡片是空的。

4. **“画布上的所有类都去分析”太危险。**
   画布是跨轮累积的，单轮最多 80 个节点，几轮下来可能两三百个。而且前端上报的“屏幕”没有相机位置，只有整图快照。所以最后定成：**节点进入画布且没有描述时才补**，不是用户点一次就给全屏发请求。

5. **“按包聚块”和现有布局有冲突。**
   现在的硬规则是“增量不跳”，新节点不能把老节点挤走；而按包重排一定会挤。另外“围着一个中心画星形”和“按包分块”也不能同时成立。最后把布局拆成两套：累积视图保持原样，另开焦点视图。

6. **代码抽屉今天没动。**
   它不在 R3 计划里，而且“效果不好”没有具体场景，先不动，等焦点视图做完再看它会不会被自然解决。

### 1.1 第一版上机后的三条反馈

服务起来后自己点了一轮，反馈三条，当天就改了：

- 关系线看着没有颜色区分（CALLS 和 DEPENDS 都偏灰）→ 换成灰 / 紫 / 蓝 / 绿四个明确色相；
- 卡片太大，画布挤 → 默认只显示类型 + 类名，包名/描述/关系数改成悬停展开；
- 接口和类看起来差不多 → 接口改成绿色徽标 + 薄荷底 + 绿色虚线，枚举改成琥珀色，类保持蓝底白线。

## 2. 最后定的方案

### 2.1 关系视觉编码（已实现）

四种关系同时用颜色、线型、箭头区分：

| 关系 | 颜色 | 线型 | 箭头 |
| --- | --- | --- | --- |
| 调用 CALLS | 灰 | 实线 | 实心 |
| 依赖 DEPENDS | 紫 | 虚线 | 实心 |
| 继承 EXTENDS | 蓝 | 粗实线 | 空心 |
| 实现 IMPLEMENTS | 绿 | 点线 | 空心 |

“接口扇出”原来也用虚线，会和依赖混，改成线上的菱形标记。图例跟着改成线型样本。

### 2.2 节点卡片（已实现，改过一版）

第一版把包名、两行描述、入出关系数全放在卡片里，卡片 104px 高，画布太挤。第二版改成：

- 默认卡片 200×56，只显示 **类型徽标 + 类名 + 断链标记**；
- 鼠标悬停（或键盘聚焦）在节点下方弹出详情卡：全限定名、核心/已描述标签、包名、最多三行描述、`入 N · 出 M`、扇出、层级；
- 核心类用左侧蓝色粗条，次核心用浅蓝细条；
- 类/接口/枚举三重区分：蓝色实心徽标 + 白底实线、绿色实心徽标 + 薄荷底虚线、琥珀徽标 + 米色底双线。

### 2.3 按需描述（已实现）

- 触发：**节点进入画布且没有描述**，不是点击触发。前端等 400ms 合并一批，每批最多 20 个，一次最多发 4 批。
- 范围：非抽象的具体类；枚举、接口、抽象类跳过；中心节点例外，强制生成。
- 已有描述的类直接跳过，前后端都判一次。
- 后端接口：`POST /api/project/{id}/class/descriptions`，单次最多 40 个，返回生成成功的条目和跳过名单；同一项目串行，失败后 30 秒内不再打 LLM。
- 存储：还是 Neo4j 的 `:Class.description`，没有新增字段。核心身份在读取时按关联度排名推导，按“项目 + 图版本号”缓存。
- Python 侧原来把描述丢了，现在补上了，REST 和 Agent 两条路看到的是同一份数据。

### 2.4 布局（只定了方案，未实现）

**累积视图**保持现在的分层/星形/增量布局，只加两件事：

- 同一节点、同一关系、同一方向超过 5 条时，把对面那几个类装进一个框，源节点画一条线到框；扇入扇出都这么处理。框可以展开，框里的类仍然可以往外连线。
- 加大节点间距，边在节点边界裁断，不再从卡片底下穿过去。

**焦点视图**作为独立标签页，和累积视图并存：

- 点一个类，单开一个“以它为中心”的画布；最多两个焦点标签页，像浏览器标签一样切换。
- 中心固定，其他节点按跳数成环、按包分块，包块默认折叠，可以展开。
- 中心到每个包只画一条线，暂时不区分“我调它”和“它调我”。
- 支持 2–3 跳；不自动切回累积视图，展开就在焦点页里展开。
- 焦点页的坐标存在标签页自己的状态里，不写回节点的 x/y，切回累积页不会乱。
- Agent 的结果只画在当前激活的页面；上报给后端的“屏幕”也只报当前页。

**200 节点以上**靠包块折叠解决。

### 2.5 还没定的细节

## 3. 今天实际改了什么

### 后端（Java）

- `ClassNodeDTO` 增加 `isAbstract`、`core`。
- `CodeGraphQueryService` 增加核心类查询：按关联度取前 20，按“项目 + 图版本号”缓存；类清单和关系查询都会带上 `core`。
- 新增按需描述接口和服务逻辑：批量、跳过已有、只描述实现类、中心强制、项目串行、失败冷却、只写回本次请求过的类。
- 分析阶段的核心类选类改为复用同一套查询，避免两处排名不一致。
- 两个受影响的单测按新逻辑更新。

### Python（Agent 服务）

- 类节点模型增加 `is_abstract`、`core`。
- 图节点模型增加 `description`、`is_abstract`、`core`。
- 生成图 patch 时不再丢描述。

### 前端（React）

- 关系线编码、空心箭头、扇出菱形标记、图例线型样本。
- 节点卡片改紧凑版 + 悬停详情；关系数改为前端按当前图实时算。
- 新增按需描述的 hook：去重、批量、占位、合并；描述失败不阻塞画布。
- 布局常量跟着卡片尺寸改；边在节点边界裁断。
- “核心类”的判断从“有没有描述”改成 `core`，类选择器、空状态、代码探索侧栏一起改。

## 5. 已知限制

1. **按需描述没有做真实端到端验证。** 接口、缓存、跳过逻辑都在，但没有在真实项目上确认“描述确实生成并写回 Neo4j”。下次开机第一件事建议先拿一个类试一下。
2. **描述失败后本会话不再重试。** 前端把请求过的节点记下来了，失败也不会反复打；要重试得刷新页面。
3. **中心节点的例外会多一次调用。** 点开接口或抽象类时，会单独发一条 force 请求。
4. **悬停详情可能被画布边缘裁掉。** 详情固定向下展开，节点在底部时看不全；还没做自动翻转。
5. **焦点视图、包块、装箱、多标签页都还没写。** 目前只有方案。
6. **“同一包只有一条线”只在焦点视图成立。** 累积视图里包内节点之间仍然是正常连线。
7. **代码抽屉完全没动。**
8. **前后端不在同一个仓库。** 后端/Agent 在 `ArchMind`，前端在 `ArchMind-react`；回滚和发布时两边要一起看。

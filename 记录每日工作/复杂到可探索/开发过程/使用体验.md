## P0 — 阻断级

### UX-01 projectId 精度丢失，导致所有按 ID 查询的工具不可用

**现象**
3 个项目的 projectId 均为 19 位十进制（≈2.12×10¹⁸），超过 JavaScript `Number.MAX_SAFE_INTEGER`（9007199254740991 ≈ 9.0×10¹⁵）。以 JSON number 传参时静默浮点化，服务端收到失真 ID。

**复现步骤**
1. `archmind_list_projects` → 得到 `2122573657964605442`
2. 以数字形式调用 `archmind_search_entities({projectId: 2122573657964605442, query: "JWT"})`
3. 实际发出的是 `2122573657964605400`（末位失真）
4. 返回 `not_found: 项目不存在`
5. 连续重试 8 次全部失败；改为**字符串**传参 `"2122573657964605442"` 后立即成功

**影响**
- 新接入方（任何 JS/TS 生态的 MCP 客户端）在无提示的情况下完全不可用
- 排查成本极高：表现像"权限问题"或"ID 抄错"，真实原因被完全掩盖

**建议**
1. Schema 放宽：`projectId: oneOf[integer, string]`，服务端 `Long.parseLong(String.valueOf(v))` 兜底
2. 或主键降位：雪花算法保证 ≤ 2⁵³
3. MCP 文档显式注明"projectId 请以字符串传递"

### UX-02 错误语义坍缩，`not_found` 的 hint 指向错误方向

**现象**

```json
{"code": "not_found", "message": "项目不存在",
 "hint": "请先用 archmind_list_projects 确认 projectId"}
```

但在已 list 过、ID 系复制所得的情况下，这条 hint 是**误导性**的：真实原因是精度丢失 / 格式非法 / 无权限，三者全被归为"项目不存在"。

**影响**
把使用者推向错误的排查路径（重查 ID），延长了故障定位时间。

**建议**
拆分错误码，并让 hint 携带可判断的信息：

| 场景 | code | hint |
| --- | --- | --- |
| 项目确不存在 | `not_found` | 请先用 archmind_list_projects 确认 |
| 存在但无权限 | `forbidden` | 当前 PAT 无权访问该项目 |
| ID 格式非法/精度丢失 | `invalid_id` | projectId 为 64 位整数，请以字符串传递 |

## P1 — 能力缺口与数据自洽

### UX-03 `trace_flow` 仅支持向下（forward），无法查询调用者

**现象**
`archmind_trace_flow` 只有 `uid` 起点 + BFS 向下，没有 `direction` 参数。

**影响**
"谁调用了这个方法/类"是排障最高频的问题，当前无法回答。本次任务中，因无法反查 `JwtAuthenticationFilter` 的注册方，只能对 `SecurityConfig → JwtAuthenticationFilter` 这条边做推测而无法验证。

**建议**
增加 `direction: forward | backward | both`（可直接对齐同类工具的 `get_call_graph` 设计）。

---

### UX-04 只有类级 uid，方法级链路不可达

**现象**
`trace_flow` 的 `uid` 是 CLASS 级，边的 `callCount` 也是类级聚合。

**影响**
本次最关键的链 `doFilterInternal → getTokenFromRequest → isWhiteList` 完全看不到。
`search_entities` 能返回方法名列表，但没有任何工具能展开到"方法 → 方法"的调用关系。

**建议**
支持 `uid` 传 `com.a.B#method` 形式，或在 `trace_flow` 增加 `level: class | method`。

---

### UX-05 缺失的边没有任何提示，`breaks: []` 制造"图完整"的假象

**现象**
`SecurityConfig`（其 `filterChain()` 方法必然注册了 JWT 过滤器）在图中**只有** `SecurityConfig → InternalTokenFilter` 一条出边，指向 `JwtAuthenticationFilter` 的边缺失。

同时返回 `"breaks": []`、`"truncated": false`。

**原因推测**（未经证实）
JWT 过滤器大概率通过字段注入 + lambda 注册，或 `@Component` 自动注册，静态分析抓不到 CALLS 边。

**影响**
agent 会默认"图是完整的"，从而漏掉关键组件——这比明确报错更危险。

**建议**
1. 对 `@Configuration` 类中被 `filterChain()` 引用的 bean，做一次"引用但无边"的兜底检查
2. 在返回中增加 `possibleMissingEdges` 或 `coverageHint` 字段
3. 文档明确：`breaks: []` 只代表"已发现的边之间无断点"，不代表"全图完整"

---

### UX-06 `edgeCount` 语义不一致

**现象**
同一个类 `JwtAuthenticationFilter`：

```
start.edgeCount      = 2
depth-0 节点.edgeCount = 0
```

**影响**
一个字段两个值，无文档说明是出边还是入边，agent 极易误判节点重要性。

**建议**
拆分为 `outEdgeCount` / `inEdgeCount`，或在 schema 中写清语义。

---

### UX-07 类级 `callCount` 聚合会误导业务解读

**现象**
`AuthServiceImpl → JwtUtil, callCount: 11`——这是**该类全部方法**合计调用 11 次，不是某条业务链路的次数。

**影响**
容易被解读成"JWT 校验调了 11 次"，从而对性能/频次做出错误判断。

**建议**
字段改名 `classLevelCallCount`，或在方法级 trace 中提供 `methodCallCount`。

---

## P2 — 输出质量

### UX-08 `layer` 的 `other` 桶过大

**现象**
`JwtUtil`、`RedisUtil`、`BusinessException` 全部落入 `layer: "other"`。

**原因**
按包名推断，在 `common.util` / `common.exception` 这类通用包上必然失效。

**好的地方**
每个节点都带 `inferred: true` + `layerBasis: "package-name"`，没有把推断伪装成事实，这点值得保留。

**建议**
增加基于**被引用关系**的补充推断（如"被 security 包高频引用 → 归入安全层"），或允许项目侧提供 `layer-mapping.yml` 覆盖。

---

### UX-09 `project_brief` 产出是 pom.xml 的复读机

**现象**
`CLAUDE.md` 草稿内容 = 项目摘要 + 技术栈（20 条）+ 分层 + 模块表。这些信息从 `pom.xml` 和目录结构就能直接得到。

图中已有的 197 个实体、调用关系，**一条都没用上**。

**影响**
作为"项目说明书"对 agent 的增量价值很低——接手项目时最缺的恰恰是"核心类在哪""主流程怎么走"。

**建议**
补充两节：

```markdown
## 核心类
- Controller：AuthController、McpPatController …
- Filter：JwtAuthenticationFilter、InternalTokenFilter
- 核心 Service：AuthServiceImpl（11 次调用 JwtUtil）

## 关键调用链
- 请求鉴权：JwtAuthenticationFilter → JwtUtil / AuthService → RedisUtil
- 登录签发：AuthController → AuthService → JwtUtil
```

---

### UX-10 `project_brief` 时间戳导致输出不可 diff

**现象**
每次调用 `生成时间` 都变（`2026-11-17 06:14:12` vs `06:53:33`），其余内容逐字相同。

**影响**
无法用 git 管理 brief 的变更；无法判断"这次生成到底改了什么"。

**建议**
拆分"内容正文"与"生成元信息"两段，元信息放独立小节或 `meta` 字段。

---

### UX-11 `overview` 缺少数据时效信息

**现象**
`meta` 有 `projectId`、`graphRev`、`index`，但**没有分析完成时间**。

**影响**
无法判断数据新旧：graphRev=1 是刚生成的还是三天前的？

**建议**
`meta` 增加 `analyzedAt` / `updatedAt`。

---

### UX-12 `index.status: "ready"` 与 `coverage: "0/0"` 是矛盾态

**现象**
`test` 项目返回 `status: "ready"`，但 `coverage` 为 `0/0`。

**影响**
"就绪但空"含义不明：是空项目、还是索引失败但状态没更新？使用者无法区分。

**建议**
新增 `empty` 状态，或增加 `entityCount` 显式字段。

---

### UX-13 `project_brief` 的 `keyFiles` 是通配符而非真实路径

**现象**

```json
"keyFiles": ["src/main/java/**/controller/**", "pom.xml（spring-boot-starter-webmvc）"]
```

**影响**
不可点击、不可 `grep`、不可直接打开，agent 拿到后还得自己做一次目录扫描才能定位。

**建议**
列出实际文件路径（如 `src/main/java/com/example/archmind/controller/AuthController.java`），通配符可作为补充说明。

## P3 — 细节

### UX-14 `search_entities` 的 `k` 上限与截断语义未文档化

返回 `meta.truncated` 一致为 `false`，但未说明 `k` 的最大值、超出时是截断还是报错。

**建议**：文档写明 `k` 范围；`truncated` 需与"语义相关度低于阈值"区分开。

### UX-15 `trace_flow` 的 `maxDepth` / `maxNodes` 触顶时缺少显式回归

未被触发，但建议在 `counts` 中体现"因 maxNodes 提前终止"，否则与"自然穷尽"无法区分。

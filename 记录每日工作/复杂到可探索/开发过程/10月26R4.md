**模型下载**
ModelScope拉BAAI/bge-m3：如何拉指令是什么？

**为什么要单独做这一步**：模型 2.3GB，如果打进镜像，每次重建都要重下。所以先下到宿主机的一个目录，再用 `-v` 挂进容器。
``` d
docker run --rm --network host -v ~/archmind/models:/models python:3.12-slim sh -c "pip install -i https://pypi.tuna.tsinghua.edu.cn/simple modelscope && modelscope download --model BAAI/bge-m3 --local_dir /models/bge-m3"
```

**逐段解释**：

- `docker run --rm` —— 临时起一个容器，用完自动删，不留垃圾
- `--network host` —— **让容器用宿主机的网络**。不加的话容器里上不了网，pip 会报“找不到这个包”
- `-v ~/archmind/models:/models` —— 把宿主机的模型目录挂到容器里的 `/models`，下载的东西就落回宿主机了
- `python:3.12-slim` —— 用个带 Python 的最小镜像当下载工具
- `modelscope download` —— 从魔搭（国内模型站）拉，不用翻 HuggingFace


**写服务**
Dockerfile+app.py(FastAPI包FlagEmbedding)
为什么要写这些内容？
这些内容怎么写？有什么根据？

 为什么需要这两份文件

你的 agent-service 是 Python 的。理论上可以直接在它里面 `import` 模型——但有两个问题：

1. **内存翻倍**。现在 agent-service 是单进程，加载一份模型 2.3GB。以后为了并发或流式输出开 2 个进程，就变成两份 4.6GB。
2. **镜像变巨大**。PyTorch 加进去要 2–3GB，而 agent-service 本身很轻。

所以拆成独立服务：模型跑在一个单独容器里，agent-service 通过 HTTP 调它。**换模型只改一个地址，不改业务代码。**

Dockerfile 是干什么的

Dockerfile 就是“怎么造这个镜像”的配方，一行一个步骤。

```
FROM python:3.12-slim          ← 从 Python 3.12 的最小系统开始WORKDIR /app                   ← 进到 /app 目录RUN pip install torch ...      ← 装 PyTorchRUN pip install FlagEmbedding ... ← 装模型库和 Web 框架COPY app.py /app/app.py        ← 把自己的代码拷进去EXPOSE 8010                    ← 声明用 8010 端口CMD ["uvicorn", ...]           ← 容器启动时跑什么
```

几个关键选择的根据：

- **`torch` 必须走 `--index-url https://download.pytorch.org/whl/cpu`**：PyPI 上的 `torch` 默认是 CUDA 版（给 NVIDIA 显卡用的），2GB 多,你根本没有 NVIDIA 卡,装了纯浪费。PyTorch 官方单独提供了一份 CPU 版,在那个地址。
- **`python:3.12-slim`**：slim 是精简版,只有 50MB 左右,不带编译器。这也正是后面出问题的伏笔——没有 gcc,任何需要现场编译的包都会失败。
- **`FlagEmbedding`**：它提供 `BGEM3FlagModel` 这个类,是 bge-m3 最直接的用法。用 `sentence-transformers` 也能加载,但拿不到 sparse。

app.py 是干什么的

它是一个小 Web 服务,对外提供一个接口：你给我文字,我给你向量。

```
model = BGEM3FlagModel("/models/bge-m3", use_fp16=False)
```

**这一行的三个根据**：

- 路径 `/models/bge-m3` 是容器里的路径,对应宿主机 `~/archmind/models/bge-m3`（靠 `-v` 挂载）
- `use_fp16=False`：fp16 是把数字精度砍一半来省内存,但**CPU 上经常不支持**,FlagEmbedding 默认开着（因为它假设你在 GPU 上跑）,所以必须显式关掉
- 这行写在文件顶层,不在函数里 —— 保证**启动时加载一次**,而不是每个请求加载一次

```
out = model.encode(texts, max_length=512, batch_size=8,                   return_dense=True, return_sparse=True)
```

- `return_dense=True, return_sparse=True` —— 这就是选 FlagEmbedding 的全部理由,两种向量都要
- `max_length=512`：模型默认能吃 8192 个字,但我们的实体卡片就一句话,吃那么多纯属浪费 CPU。**这是纯 CPU 环境下最值得调的一个参数**
- `batch_size=8`：一次处理 8 条,CPU 上再大反而慢

```
@app.post("/embed")     ← 收文字,还向量
@app.get("/health")     ← 只回答"我活着",给监控/排查用
```

**构建镜像**
构建镜像为什么经常出问题，如何解决的

问题1：Run pip install被当成shell命令
报错：RUN未找到命令。RUN是Dockerfile里的词，不是终端命令，只有在docker build读Dockerfile的时候才生效。解决先写文件在构建

问题2：容器连不上网
报 `Could not find a version that satisfies the requirement FlagEmbedding (from versions: none)`。

**这句话极具迷惑性**——它看起来像"没有这个包",实际意思是"我连不上仓库,所以什么版本都没看到"。秒回就是网络问题,不是包的问题。

**解决：给构建加 `--network host`**,让构建过程用宿主机的网络

问题3：pip路往回退版本

日志里出现 `aiohttp 3.8.1 → 3.8.0 → 3.7.4`,每个都要下载源码包。
原因链条：`FlagEmbedding` 依赖 `datasets`,`datasets` 依赖 `aiohttp`。但 Python 3.12 出来时,aiohttp 3.8 还没发布,所以**没有适配 3.12 的预编译包**。pip 拿不到现成的,只能下源码现场编译;而 slim 镜像没有编译器,编不了。
pip 遇到这种情况不会立刻报错,而是想"也许更老的版本可以",于是退到 3.8.0、3.7.4……**这是一条必然失败的路,但每条都要花几分钟才走完**。

**解决：在安装列表里加 `"aiohttp>=3.9"`,强制它不许低于 3.9。** 3.9 之后的版本有 3.12 的预编译包,pip 直接拿现成的,不编译。
问题 4：下载速度 50 kB/s
pypi.org（官方源）在实验室网络下慢得离谱。**解决：换成阿里云镜像。**
**注意问题 3 和 4 是两件事,必须都修**——只换源,还是在回溯里耗一小时;只钉版本,还是慢
最终的构建命令
```
docker build --network host --progress=plain -t archmind-embed ~/archmind/embedding
```

- `-t archmind-embed` —— 给镜像起名字
- `--progress=plain` —— 输出完整日志,不然出错只给你一行
- 最后那个路径是 Dockerfile 所在目录


**启动容器**
如何启动的，指令是什么
如何看是否正常，判断依据是什么

 启动容器指令

```
docker run -d --name archmind-embed --restart unless-stopped --cpus=3 -p 8010:8010 -v ~/archmind/models:/models archmind-embed
```

逐段：

- `-d` —— 后台跑,不占着终端
- `--name archmind-embed` —— 起个名字,以后 `docker logs` / `docker stop` 用得到
- `--restart unless-stopped` —— 服务器重启后自己起来（除非你手动停过）
- `--cpus=3` —— **只给它 3 个核**。机器总共 4 核 8 线程,还要养 Neo4j、MySQL、Java。不限制的话,建索引那十几分钟接口会明显变慢
- `-p 8010:8010` —— 宿主机 8010 端口对到容器 8010
- `-v ~/archmind/models:/models` —— 把模型挂进去
- 最后 `archmind-embed` 是镜像名

如何判断正常：
**第一层：进程起来了**

```
docker logs -f archmind-embed
```

看到 `Uvicorn running on http://0.0.0.0:8010` 就说明服务进程启动成功。

⚠️ 按 `Ctrl-C` 只是退出日志,**不会停容器**,这是 `logs -f` 的特性。

**第二层：接口能通**

```
curl -s http://127.0.0.1:8010/health
```

返回 `{"ok":true}`。这一步只证明 Web 服务活着,**不代表模型加载成功**。

**第三层：模型真的在干活**

```
curl -s -X POST http://127.0.0.1:8010/embed -H 'Content-Type: application/json' -d '{"texts":["下单扣库存"]}' | python3 -c "import sys,json; d=json.load(sys.stdin); print('dense', len(d['dense'][0]), '| sparse', len(d['sparse'][0]))"
```

返回 `dense 1024 | sparse 5`。

**为什么 1024 是硬标准**：bge-m3 的输出维度是固定的 1024。不是 1024 就说明加载的不是这个模型,或者加载错了。

**第四层：语义真的有用**

前一层只证明"能算出数字",不证明"算得对"。所以要拿几个已知相关/无关的句子比一比：

```
python3 -c "import json,urllib.request as u; c=['负责订单创建、取消的核心业务逻辑','负责用户登录、注册与鉴权','负责库存查询与扣减','订单相关的 HTTP 接口入口']; t=['下单要扣库存，代码从哪进的']+c; r=u.Request('http://127.0.0.1:8010/embed',data=json.dumps({'texts':t}).encode(),headers={'Content-Type':'application/json'}); v=json.load(u.urlopen(r))['dense']; q=v[0]; [print(round(sum(a*b for a,b in zip(q,x)),4), s) for s,x in zip(c,v[1:])]"
```

结果：

```
0.7485  负责库存查询与扣减        ← 对0.6295  订单相关的 HTTP 接口入口   ← 相关0.5830  负责订单创建、取消的核心业务逻辑0.4597  负责用户登录、注册与鉴权   ← 无关,垫底
```

**这四层的意义**：如果只做到第三层,你会以为一切正常;做到第四层才发现——**裸类名 `OrderServiceImpl` 的得分比无关的「用户登录注册」还低**。这个发现直接决定了后面实体卡片必须写描述,不能只放类名。

我的心智模型与当前开发的内容不是同一层内容，导致对项目进展有所迷茫。

我认为的agent开发是：
用户需求---提示词---定义Tool---LLM调用---边界条件---Context设计

这是一个agent开发的正确的完整描述，但是这一切的成立需要一个默认前提：

-  Tool返回的数据是否可行，是否有界，是否可追溯。（evidence：存放可追溯的证据）
- LLM不知道数据不全，不会自己编数据（truncate：当前数据是否全，note：有多少数据，给了多少数据）
- Python能够调用java侧Tool（需要是通路，需要有token验证把关）

## 为什么我想不到"撞墙"，因为它是产品本身

心智模式是理想化了所有内容后的完整链路，但是实际上，真实的代码的调用关系不一定是完整的，是会断开的，接口是一处断口，实际调用的是接口的实现。这些问题不是心智模型告诉你的，是针对产品本身所需要做出的应对和改变。

实际的应用：9个模块18个类，两个同名的类，跨服务调用。所以真实企业级agent不是简单的tool调用，而是实际面对的复杂的业务中需要解决的各种问题

### 为什么我想不到需要建立什么文件？

文件规则：
同一个文件里的东西，应该因为同一个原因而改变。
对着你项目的实际文件看：

|文件|它负责|什么时候要改它|
|---|---|---|
|models/tool.py|契约长什么样|**Java 的 DTO 改了**|
|`java_client.py`|怎么把请求发出去|**URL / 超时 / token 改了**|
|`config.py`|配置从哪来|加了新环境变量|
|`main.py`|服务怎么启动|几乎不变|
|api/agent.py|对外暴露哪些路由|加接口时|

**为什么 `tool.py` 和 `java_client.py` 必须分开？** 因为它们的**变化原因完全不同**。Java 加个字段 → 只改 `tool.py`；服务器换地址 → 只改 `java_client.py`。如果混在一起，改一个会碰到另一个


### 各种字段的设计原因

因为 `tool.py` 里的字段来自**三个完全不同的来源**，你把它们当成一类东西在看，当然觉得莫名其妙。

|来源|字段|拦的是哪个问题|
|---|---|---|
|**安全/诚实**|`ok` `evidence` `truncated` `note` `graphRev`|LLM **编造 / 把部分说成全部 / 引用了不存在的东西**|
|**图语义**|`nodes` `edges` `gaps` `viaFanout` `depth`|调用链**怎么表达**、断点**为什么断**|
|**预算控制**|`maxDepth` `maxNodes` `maxMethods` `maxLines`|**别把 prompt 撑爆 / 别把 Neo4j 打爆**|

**验证你是不是真懂一个字段，只有一个测试：能不能说出"如果删掉它，会发生什么具体的错误"。**

举例：
- 删掉 `truncated` → LLM 把"**我只看到 3 个**"讲成"**这个类只调用了 3 个**"，用户被误导，而且句子读起来完全正常 → **最难发现的错误**
- 删掉 `evidence` → LLM 引用一个不存在的 uid，前端点了没反应，无法归因
- 删掉 `graphRev` → 用户中途点了"重新分析"，agent 拿旧数据讲，和屏幕上看到的不符
- 删掉 `viaFanout` → 用户看到一个实现类，以为它是被直接调用的，其实源头是接口

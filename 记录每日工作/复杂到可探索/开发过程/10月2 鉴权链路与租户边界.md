# 10月2 鉴权链路与租户边界

> 巩固 [10月1 Agent 阶段巩固清单](10月1%20Agent%20阶段巩固清单.md) 里 A 块的四个问题（Q2/Q3/Q4/Q6），把它们从「背答案」变成「能讲清原理」。
> 今天搞懂的核心一句话：**项目里其实有两条完全不同的鉴权线——用户身份（JWT）和服务身份（共享密钥），混在一起就全乱。**

---

## 1. 为什么 Python 直连 Neo4j 会绕过租户验证

**一句话：租户校验是 Java 业务层里的一条 if，Neo4j 本身不知道「哪个 project 属于哪个用户」。直连就是跳过这条 if，直接对库跑 Cypher。**

具象化场景：

- 用户 A 登录，项目 `projectId=1`；用户 B 有 `projectId=2`。
- **走 Java**：查询前先 `CheckProjectUtil.checkProject(userId, projectId)`，确认 projectId 属于当前用户，不属于就拒。
- **直连**：Python 拿到 `projectId=2`，直接 `MATCH (n:Class) WHERE n.projectId = 2 RETURN n`。Neo4j 没有用户概念、没有归属表，你要 2 就给 2。于是 A 只要让 Python 发一个 `project_id=2`，就把 B 的项目图谱拖出来了。

**为什么这么容易漏？** P4 之前这条链本来就不完整——`CheckProjectUtil.checkProject` 还没补，`projectId` 现在就是「调用方给的」。只要 Python 能直连，这个 projectId 就成了**没有任何校验的查询参数**，抓包改一下就能横跳。

直连的另外两层代价（清单 Q2 的 ②③）：
- ② 造出第二份数据副本：Python 一套 Cypher、Java 一套 Cypher，图和实现分家。
- ③ 分布式单体（见下）。

**硬证据**：`agent-service/requirements.txt` 里没有 `neo4j` / `pymysql`，只有 `fastapi uvicorn pydantic pydantic-settings httpx pytest pytest-asyncio`。边界能靠依赖清单证明。

## 2. 分布式单体是什么

**进程拆了、部署拆了，但边界没拆——两个服务共享数据库。** 付出了分布式的全部成本（网络延迟、故障、一致性、难排错），却没拿到任何收益（独立演进、独立部署、故障隔离）。一句话：**拆了，但没隔离。**

和真正微服务的区别：

| 维度 | 分布式单体（坏） | 微服务（好） |
| --- | --- | --- |
| 数据所有权 | 两个服务连同一个库，谁都能读能写 | 每个服务独占自己的数据 |
| 通信 | 靠共享表 / 直连数据库 | 只靠 API 契约 |
| 改动影响 | 一个服务改表结构，另一个直接炸 | 改内部实现，对别人无感 |
| 部署 | 表面能分开部署，实际一改要一起上 | 真正独立部署、独立伸缩 |

**为什么会设计出它：按语言拆，不按边界拆。** 经典翻车路径：「因为 LLM 用 Python 写方便，拆个 Python 服务」→ 拆完让 Python 直接连 Neo4j/MySQL 拿数据 → 两个服务共享一个库，边界塌了。

**本项目的正确姿势（清单 Q1）**：按数据所有权切——Java 独占 MySQL/Neo4j/磁盘/JWT（有状态、要事务）；Python 独占 LLM 和会话 Context（无状态、要频繁换模型）。Python 想要图数据只能走 Java 的 `/internal/tools`，不能自己连库。**用 API 契约替代共享数据库，是避免分布式单体的核心动作。**

## 3. `X-Internal-Token` 不是「用户 token 加前缀」

**纠正一个我之前的误解：它不是用户 token 加前缀，它是 Java 和 Python 之间预先约定的一把完全独立的固定密钥**（一段随机字符串），和用户 JWT 没有任何关系。

这个区分背后是两个不同层次的身份：

| 层次 | 验证什么 | 用什么 |
| --- | --- | --- |
| 用户身份 | 「这个人是谁、有没有权限」 | 用户 JWT（只在 Java 侧验证） |
| 服务身份 | 「调用方是不是 Java 服务本身」 | `X-Internal-Token` 共享密钥 |

**为什么需要共享密钥，而不是把用户 JWT 转发给 Python？** 因为要「让 user token 在结构上不可能泄进 LLM prompt」（清单 Q4）。Python 的职责就是把东西喂给 LLM——一旦用户身份进了 Python 进程，就有被拼进 prompt 的风险。所以 Python 只拿得到 `projectId` 这个数字，拿不到任何身份。

同时 Java → Python 这段调用本身也要认证：什么都不验证的话，任何能摸到 Python 端口的进程都能冒充 Java 调工具接口。所以用一把独立共享密钥表达「这是 Java 内部发来的可信调用」，但它**不表达「用户是谁」**。

**三段验证各回答一个问题**：
- 用户 → Java：JWT，回答「用户是谁」。
- Java → Python：`X-Internal-Token` 共享密钥，回答「是 Java 在调我」。
- Python → Java（/internal/tools）：同一把共享密钥，Java 侧 `InternalTokenFilter` 验，回答「是 Python 在调我」。

JWT 验证的是人，共享密钥验证的是服务——两件事，不能互相替代。

## 4. 完整鉴权链路 + 为什么「共享密钥 + 防时序侧信道」就够

### 完整链路（按数据流走一遍）

```
用户 ──JWT──▶ Java 网关/控制器 ──验证JWT──▶ 确认用户身份+权限
                                            │ 需要 LLM 相关逻辑
                                            ▼
                        Java ──X-Internal-Token──▶ Python
                                            │ require_internal_token:
                                            │   拿头 → compare_digest 比较 → 相等才放行
                                            ▼
                        Python 只用明文 projectId 干活（无用户身份）

Python 查图 ──X-Internal-Token──▶ Java /internal/tools
                                            │ InternalTokenFilter 验共享密钥
                                            ▼
                        Java 返回图数据（Java 侧已知用户上下文）
```

关键点：**用户 JWT 只存在于「用户 → Java」这一跳，Python 进程里自始至终没有身份。**

### 为什么够用

「够用」不是因为这把密钥多高级，而是因为**即使密钥被破，能偷到的东西也极其有限**（清单 Q5）——Python 只有明文 `projectId` + 5 个只读工具接口，拿不到用户身份、JWT、数据库凭据。

所以「共享密钥」这个相对轻量的认证，在「**内部网络 + 只读接口 + 无敏感数据**」三个约束下是充分够用的。真要对外暴露、多机器多服务，才需要上 mTLS / 服务网格（清单 Q6 的演进方向）——**能说出这个边界才算懂**。

### 时序侧信道是什么

「时序侧信道」是攻击方式，不是通信方式。普通 `==` 是逐字节比较：第一个字节不匹配就越早返回，攻击者测响应时间就能**一个字节一个字节猜出密钥**。`secrets.compare_digest` 是定长比较——不管对不对都把所有字节比完，耗时恒定，时间泄露不出任何信息，堵住这条侧信道。

代码落点：`app/api/agent.py:33` 用 `secrets.compare_digest`，注释写「和 Java 侧 `InternalTokenFilter` 的做法对齐」；`config.py` 的 `INTERNAL_TOKEN_HEADER` 是两边共用的常量名，注释「写在一处，改的时候不会只改一半」。

## 今天真正想通的一点

之前我把鉴权当成「一件事」在看，所以会问出「JWT 都验证过了为什么还要共享密钥」这种问题。其实它是**两条正交的线**：

1. **用户身份**——验证「人」，只在 Java 边界发生，绝不进 Python（防泄进 prompt）。
2. **服务身份**——验证「进程」，用一把独立的共享密钥，两边互认。

想通这个分层，Q2/Q4/Q6 就全串起来了：直连 Neo4j 会漏，是因为跳过了用户身份那条线的业务校验；共享密钥够用，是因为服务身份那条线之外，Python 手里根本没有值钱的东西。

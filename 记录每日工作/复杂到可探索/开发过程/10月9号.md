为什么需要redis？
1. 多worker会静默串会话
定义：多个请求在并发处理或跨 Worker 调度时，错误地读取、修改或混用了其他会话的状态，而且系统不一定会报错。

例如，你的 Agent 服务部署了两个 Worker：

- Worker A 处理用户甲的请求，当前上下文是 `OrderService`。
    
- Worker B 处理用户乙的请求，当前上下文是 `UserService`。
    

如果会话状态被错误地放在共享变量中，或者读取历史时没有正确使用 `sessionId`，用户甲追问“这个类调用了哪些方法？”时，就可能拿到用户乙的上下文。

这种问题危险在于：请求可能正常返回，但回答对象错了，甚至造成跨用户数据泄露。

需要重点学习：

- `sessionId` 如何唯一标识一个会话。
    
- 会话状态为什么不能依赖 Worker 的局部内存。
    
- Redis、数据库如何支持多 Worker 共享状态。
    
- 同一会话的并发请求如何保证消息顺序和状态一致性。
    
- 如何通过 `userId + sessionId` 校验会话归属，防止越权访问。
    

注意：多 Worker 本身不会导致串会话。根因是状态隔离、共享存储或并发控制设计不当。


2. 重启即丢失
   核心问题是：Agent服务重启之后，能否恢复之前的会话和执行状态？
   存储方式：
	   进程内存，当进程退出后状态丢失，无法恢复历史
	   Redis，通常可以重新读取，取决于持久化，故障恢复，淘汰策略
	   Mysql数据库，通常可以恢复已提交数据，需要设计数据模型和恢复逻辑
	
	对话恢复：能够重新读取之前俺的消息，继续回答用户
	任务恢复：能够识别重启前未完成的Agent任务，并决定恢复，重试或标记失败
	
	agent还需要保存任务状态和必要的工具调用记录
	
	重点学习持久化，事务，故障恢复，幂等性，和任务状态机
   
2. TTL天然表达会话语义（Time To Live表示数据的生存时间）
   表示会话在一段时间没有活动后失效

   例如，设置 30 分钟的滑动 TTL：

| 时间    | 操作     | 结果              |
| ----- | ------ | --------------- |
| 10:00 | 创建会话   | TTL 为 30 分钟     |
| 10:10 | 用户继续提问 | TTL 重置为 30 分钟   |
| 10:25 | 用户再次提问 | TTL 再次重置为 30 分钟 |
| 10:55 | 没有后续活动 | 会话过期            |
   需要理解两种TTL：
   - 固定TTL：从创建或治党时间点起，经过固定时长后过期
   - 活动那个TTL：每次有效活动后重新计算过期时间
     
    TTL不等于会话管理，仍需要定义会话创建，续期，关闭，恢复以及过期后的行为
   
3. evict才能真删干净
   Java 删项目时要清掉该项目的**全部**会话（agent.py:152）。内存 dict 只能清本进程的；Redis 能按前缀删所有 worker 的。
   
   Evict通常翻译为淘汰，指系统根据策略移除数据，以释放有限存储资源

	它和另外两个概念的区别是：

| 概念     | 含义            | 示例           |
| ------ | ------------- | ------------ |
| Expire | 数据超过有效期       | 会话 30 分钟没有活动 |
| Evict  | 系统按资源管理策略淘汰数据 | Redis 内存达到上限 |
| Delete | 应用主动删除数据      | 用户删除某个会话     |

以 Redis 为例，常见淘汰策略包括：

- `noeviction`：达到内存上限后，不主动淘汰已有键，部分写操作可能失败。
    
- `allkeys-lru`：从所有键中优先淘汰最近较少访问的键。
    
- `volatile-lru`：从设置了过期时间的键中选择淘汰对象。
    
- `allkeys-lfu`：优先淘汰访问频率较低的键。

如果重要的上下文只存在 Redis 中，一次淘汰就可能让会话丢失。更稳妥的方式是把需要长期保留的消息放入数据库，把 Redis 用作活跃状态缓存，并设计缓存失效后的恢复机制。

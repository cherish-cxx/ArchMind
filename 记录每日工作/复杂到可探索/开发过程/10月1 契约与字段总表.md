## 0. 契约的四条规定（**这才是"按什么规定"的答案**）

### 规定 1：名字逐个对齐，**不做 Python 风格改写**
Java 叫 `qualifiedName`，Python 就写 `qualified_name` —— 但 JSON 里必须还原成 `qualifiedName`。
**任何"顺手改名"都会丢字段**，且丢得无声无息。

### 规定 2：驼峰 ↔ 蛇形自动转换，靠 `CamelModel`

```python
# agent-service/app/models/base.py
class CamelModel(BaseModel):
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)
```

| 效果 | 说明 |
| --- | --- |
| 输出 | Python 的 `qualified_name` 序列化成 JSON 时自动是 `qualifiedName` |
| 输入 | JSON 的 `qualifiedName` 自动映射回 `qualified_name` |
| `populate_by_name=True` | **额外**允许用蛇形名直接构造（`ClassNode(qualified_name=...)`），方便测试和内部代码 |

所有契约模型都继承它，所以**不存在手写 alias 的情况**（唯二的例外见规定 5 的 `from`）。

### 规定 3：Java 可能发 `null` 的字段，类型里**必须**带 `| None`

Java 没配 Jackson 的 `NON_NULL`，**可为空的字段会真的发成 `"key": null`**。
而 Pydantic 的 `= 默认值` **只在「键不存在」时生效，对显式 null 无效**：

```python
note: str | None = None     # ✅ null 能过
note: str = None            # ❌ Java 发 null 时直接 ValidationError
```

### 规定 4：Java **原始类型**（`boolean` / `int`）→ Python **必填、不给默认值**

因为原始类型在 Java 里不可能为 null，**一定会发**。给默认值的危害是：
一旦哪天真的缺失，默认值会把「缺失」伪装成「一个正常值」。

最典型的是 `truncated`：

```python
truncated: bool            # ✅ 故意不给默认值
# 一旦默认成 False，就会把「被截断」讲成「完整」—— 这是最难发现的错误
```

### 规定 5：同名不同物 —— `evidence` 有两个

| 位置 | Java 类型 | 含义 |
| --- | --- | --- |
| 信封里 `ToolEnvelope.evidence` | `List<Evidence>`（**结构化**） | 机器校验的凭据：`from` / `to` / `rel` / `count` |
| 数据里 `RelatedClassDTO.evidence` | `List<String>`（**给人看的短句**） | 如 `"handleLogin(String,String) → login(String,String)"` |

**面试点**：这两个只可校验前者。所以 `citations ⊆ evidence` 里的 evidence 指的是**信封那个**。

## 1. 核心概念：uid

| 实体 | uid 格式 | 例 |
| --- | --- | --- |
| **类 / 接口 / 枚举** | **全限定名** | `com.hmall.trade.controller.OrderController` |
| **方法** | `owner#signature` | `com.hmall.trade.service.IOrderService#createOrder(...)` |

**uid 的三条性质（设计 §7 决定①「只用 uid 引用，不存对象」的理由）**：

1. **是图的唯一键** —— Neo4j 里节点的标识，天然稳定
2. **天然可校验** —— 字符串能不能在图里找到，一句话的事（这是 `guard` 的基础）
3. **不携带对象** —— Context 里只存字符串，不存类对象/代码片段，所以 Context 不会膨胀

**代码落点**：`ClassNodeDTO.qualifiedName` 的注释原文就写着「全限定名，即图中节点的 uid」。
Python 侧取短名的地方在 `agent-service/app/core/explain.py` 的 `_simple()`：

```python
uid.split("#", 1)[0].rsplit(".", 1)[-1]   # 先砍掉方法签名，再取最后一段包名
```

## 2. 请求契约：一次工具调用

```
POST /internal/tools/{overview|classes|class-relations|call-chain|method-body}
Header: X-Internal-Token: <共享密钥>          ← 不走 JWT
Body:   { "projectId": <long>, "args": { ... } }
```

```java
// ArchMind/.../dto/request/InternalToolRequest.java
public class InternalToolRequest {
    private Long projectId;
    private Map<String, Object> args = new HashMap<>();
}
```

> ⚠️ **Python 侧不定义这个模型**。`java_client` 手工构造 `{"projectId": ..., "args": ...}`，
> 因为 `args` 是**每个工具不同的自由字典**，用 Pydantic 反而碍事。

### 每个工具的 `args` 精确取值

| 工具 | args key | 类型 | 不给时 | 上限 |
| --- | --- | --- | --- | --- |
| `overview` | *（无）* | — | — | — |
| `classes` | `limit` | number | 40 | clamp 到 ≤200 |
| `class-relations` | `uid` | string | **必填** | — |
| | `direction` | string | `BOTH` | 非法值 → **拒绝**（不是兜底） |
| | `limit` | number | 40 | clamp 到 ≤200 |
| `call-chain` | `uid` | string | **必填** | — |
| | `direction` | string | `DOWN` | 只有 DOWN/UP，**没有 BOTH** |
| | `methodUid` | string | 不传 | — |
| | `maxDepth` | **number** | 2 | clamp 到 ≤3 |
| | `maxNodes` | **number** | 40 | clamp 到 ≤200 |
| `method-body` | `uid` | string | 二选一 | — |
| | `methodUid` | string | 二选一 | — |
| | `maxMethods` | number | 3 | — |
| | `maxLines` | number | 120 | — |

### ⚠️ 取参数的实现（**"参数静默降级"的根源**）

```java
// ArchMind/.../controller/InternalToolController.java:314-322
private int intArg(Map<String, Object> args, String key, int fallback) {
    Object raw = args == null ? null : args.get(key);
    return raw instanceof Number n ? n.intValue() : fallback;   // ← 不是 Number 就吃默认值，不报错
}

private String strArg(Map<String, Object> args, String key) {
    Object raw = args == null ? null : args.get(key);
    return raw == null ? null : String.valueOf(raw).trim();
}
```

**两条会导致静默失效的规则**：
1. **key 名字必须完全一致**（`maxDepth` 写成 `max_depth` → 找不到 → 吃默认值 2）
2. **数字必须是 JSON number**（发 `"2"` → `raw instanceof Number` 为 false → 吃默认值）

> 唯一**不**静默兜底的是 `direction`：`parseDirection()` 遇到非法值返回 `null`，
> 由调用方显式拒绝（HTTP 200 + `ok:false`）。这是刻意的对照设计。

### 硬上限一览（**设计文档写过 40，是错的**）

| 常量 | 值 | 位置 |
| --- | --- | --- |
| `DEFAULT_LIMIT` | 40 | `InternalToolController:48` |
| `MAX_LIMIT` | 200 | `InternalToolController:49` |
| `DEFAULT_CHAIN_DEPTH` | 2 | `InternalToolController:51` |
| `DEFAULT_MAX_METHODS` | 3 | `InternalToolController:53` |
| `DEFAULT_MAX_LINES` | 120 | `InternalToolController:54` |
| **`MAX_DEPTH_HARD`** | **3** | `CallChainServiceImpl:44` |
| **`MAX_NODES_HARD`** | **200** | `CallChainServiceImpl:45` |

```java
// CallChainServiceImpl:115-116 —— 是 clamp，不是拒绝
int depth = Math.max(1, Math.min(maxDepth, MAX_DEPTH_HARD));
int nodes = Math.max(1, Math.min(maxNodes, MAX_NODES_HARD));
```

**结论**：Java 会 clamp 到 200/3，但**不会替 Agent 拦到 40**。
想让预算真的是 40，只能 Python 显式传 —— 这就是 `java_client` 顶部「约束③」的含义。

## 3. 响应契约：信封（五个工具共用）

```java
// ArchMind/.../dto/response/ToolEnvelope.java
private final boolean ok;
private final T data;
private final List<Evidence> evidence;
private final boolean truncated;
private final String note;
private final Long graphRev;
```

```python
# agent-service/app/models/tool.py:90-102
class ToolEnvelope(CamelModel, Generic[T]):
    ok: bool
    data: T | None = None
    evidence: list[Evidence] = []
    truncated: bool
    note: str | None = None
    graph_rev: int = 0
```

| 字段 | 含义 | 要点 |
| --- | --- | --- |
| `ok` | 业务是否成功 | **失败仍走 HTTP 200**，不是异常 |
| `data` | 工具数据，形状由泛型 `T` 决定 | `ok=false` 时为 `null` |
| `evidence` | 结构化凭据 | ★ grounding 的唯一基准 |
| `truncated` | 结果是否被截断 | ★ **不给默认值**（规定 4） |
| `note` | 失败原因 / 降级说明 | 原样转述给用户，不美化 |
| `graphRev` | 图版本号 | ⚠️ Java 是包装类 `Long`（可 null），Python 给 0 兜底 |

**`graphRev` 的两个细节**：
```java
// InternalToolController:237-240 —— 唯一一处盖章
private <T> ToolEnvelope<T> stamp(ToolEnvelope<T> envelope, Long projectId) {
    return envelope.withGraphRev(graphRevService.currentRev(projectId));
}
```
1. **五个工具统一在这里盖**，所以实际不会为 null（Python 的 `= 0` 是防御）
2. **失败响应也盖章**（`ok:false` 也带 rev）—— 注释原文：「类不存在很可能是图被重建过导致的，调用方正是需要 rev 才能判断自己的 Context 是否已过期」

### Evidence（信封里的那个）

```java
private String kind;    // EDGE / CLASS / METHOD / FILE
private String from;    // 起点：类全限定名，或方法 uid
private String to;      // 终点；kind=CLASS/FILE 时可为空
private String rel;     // CALLS / EXTENDS / IMPLEMENTS / DEPENDS
private Integer count;  // 同一对端点之间的聚合条数
```

```python
# models/tool.py:77-87
class Evidence(CamelModel):
    kind: EvidenceKind
    from_: str = Field(alias="from")   # ← 唯二手写 alias，因为 from 是 Python 关键字
    to: str | None = None
    rel: RelationType | None = None
    count: int | None = None
```

## 4. 五个工具的 data 形状

### ① overview → `ProjectOverview`

```java
// ProjectOverviewResponse.java —— 数据源是 project_overview 表的 JSON 列（LLM 生成）
private String projectType;  private String summary;  private String description;
private List<TechStackItem> techStack;   // {name, category, version, role}
private Architecture architecture;       // {style, layers[], description}
private List<ModuleItem> modules;        // {name, responsibility, keyFiles[]}
```

> **Python 侧这一组故意全宽松**（每个字段 `| None`）。理由：overview 是**降级路径**（图挂了它还得能答），
> 而它的数据是 LLM 编的、大面积缺失是常态。缺字段只会让讲解变少，不会让讲解变错。

### ② classes → `list[ClassNode]`

### ③ class-relations → `ClassRelations`

```java
private ClassNodeDTO center;
private Upstream upstream;      // {callers[], dependents[], subclasses[]}
private Downstream downstream;  // {callees[], dependencies[], parents[]}
// 每一项都是 RelatedClassDTO { clazz: ClassNodeDTO, relationType: String, evidence: List<String> }
```

| 字段 | 中文 | 语义 |
| --- | --- | --- |
| `callers` | 谁调我 | 方法级 `CALLS` 入边（**只看直接边**） |
| `dependents` | 谁依赖我 | 类级 `DEPENDS`（字段/签名类型指向我） |
| `subclasses` | 谁继承/实现我 | `EXTENDS` / `IMPLEMENTS` |
| `callees` | 我调谁 | 方法级 `CALLS` 出边 |
| `dependencies` | 我依赖谁 | 类级 `DEPENDS` |
| `parents` | 我继承/实现谁 | `EXTENDS` / `IMPLEMENTS` |

> ⚠️ `upstream` / `downstream` **可以是 null** —— 因为控制器按 `direction` 只跑需要的那一侧
> （「原来固定跑 6 条 Cypher，单方向调用会白跑 5 条」）。

### ④ call-chain → `CallChain`

```java
private ClassNodeDTO start;
private List<ChainNode> nodes;   // {uid, name, kind, module, depth, viaFanout, edgeCount}
private List<ChainEdge> edges;   // {from, to, rel, callCount, viaFanout}
private List<Gap> gaps;          // {at, reason}
private boolean truncated;
```

| 字段 | 含义 |
| --- | --- |
| `viaFanout` | 这条/这个节点是**经接口扇出**过来的（不是直接调用） |
| `depth` | 层数。**扇出不计 depth** |
| `edgeCount` | 聚合了多少条方法级边 |
| `module` | 从 `filePath` 推导，推不出来就是 null |
| `Gap.at` | 断在哪个 uid |
| `Gap.reason` | `REMOTE_SERVICE` / `INTERFACE_NO_IMPLEMENTATION` / `NO_DOWNSTREAM_EDGE` / `EXTERNAL_DEPENDENCY` |

> 后两个 `GapReason` 是**保留值，V1 不产出**。

### ⑤ method-body → `MethodBody`

```java
private List<MethodCode> methods;  // {uid, signature, owner, startLine, endLine, code, error, resolvedFrom}
private boolean truncated;
private String note;               // 降级说明
```

| 字段 | 含义 |
| --- | --- |
| `startLine` | **从第一个注解算起**（`@GlobalTransactional` 会被切进去，javadoc 不会） |
| `resolvedFrom` | ★ 请求的是接口方法、实际切了实现类时，填**原接口方法 uid** |
| `error` | 源码读不到时的原因 |

## 7. 一页速查：字段对照表

| 概念 | Java | JSON | Python |
| --- | --- | --- | --- |
| 类节点的唯一键 | `qualifiedName` | `qualifiedName` | `qualified_name` |
| 信封成功标志 | `ok` | `ok` | `ok` |
| 信封数据 | `data` (T) | `data` | `data: T \| None` |
| 结构化凭据 | `evidence` (List\<Evidence\>) | `evidence` | `evidence: list[Evidence]` |
| 凭据起点 | `from` | `from` | `from_` (alias="from") |
| 截断标志 | `truncated` | `truncated` | `truncated: bool`（无默认） |
| 失败原因 | `note` | `note` | `note: str \| None` |
| 图版本 | `graphRev` (Long) | `graphRev` | `graph_rev: int = 0` |
| 请求体 | `projectId` + `args` | 同 | 不建模，`java_client` 手构 |
| 调用的方向 | `direction` | `direction` | `ChainDirection` / `RelationDirection` |
| 关联方向枚举 | 两个独立枚举 | — | `ChainDirection`(2) / `RelationDirection`(3) |

> ⚠️ **`ChainDirection` 和 `RelationDirection` 是两个枚举，别图省事合成一个**：
> 前者只有 DOWN/UP（多层 BFS vs 单层反查），后者有 DOWN/UP/**BOTH**。
> Python 侧 `models/tool.py:50-62` 分开定义，`tests/test_contract.py::test_3` 专门盯这件事。

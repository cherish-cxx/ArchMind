问题：
一轮只能差一个工具，这是核心体验问题
目前的链路是：`Intent` 六选一 → `INTENT_TOOL` 查表 → 调一个工具 → 讲解。`loop.py:115` 之后只执行一次；唯一的“第二步”是 `method_uid` 锁定时补一次 `method-body`（`loop.py:162-173`），是硬编码特例，不是通用能力。

后果：
- 用户问“OrderService 的支付流程”，查到 `OrderClient` 是接口就停了，回答只能说“这里是跨服务断点/断链”，**不能自己再查一次实现类**；
- 接口 → 实现、Controller → Service → Mapper、断点后的下游，全都需要用户再点一次或再问一轮；

当前的工具不在数据里，模型看到的不是工具定义，而是prompt里一顿啊自然语言规则；参数由slots这套为意图服务的小结构携带

判断和执行是两次独立的LLM，结果不能反过来影响下一步

 预算和去重形同虚设
`Budget` 里 `steps_used` 从来没有递增，`tool_calls_limit / steps_limit` 从来没有被执行（只有 `tool_calls_this_turn` 在 `loop.py:137` 加一）。单步时无害，一开多步就会失控，而且重复调用没有防护。

 错误是异常流，不是数据
`ToolTransportError` 直接短路成 `_tool_down` 降级；`InternalAuthError` 往上抛。单步时可以这么写，多步循环里需要的是“这次工具失败了，把失败原因作为一条 observation 喂回模型，让它换个查法”，而不是整轮终止。

证据、注入、出图都按“单结果”写死
`evidence_uids(envelopes)` 虽然收列表，但全链路默认一个 envelope（加那个特例）；`explain` 的优先级、`ui_commands` 的推导也是按单结果设计的。多工具并集、引用白名单、UI 指令优先级都要重新收口。

可观测性不足
`steps` 只有 INTENT / TOOL / LLM，没有 PLAN。多步之后用户看不到“它先查了什么、为什么又查了一次”，调试和演示都吃亏。

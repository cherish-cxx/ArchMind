## 1. 当前上下文是怎么存的

### 1.1 三层

| 层 | 存什么 | 位置 |
| --- | --- | --- |
| 前端 | 完整聊天记录（只在内存，刷新即丢） | `ArchMind-react/src/state/conversationStore.js` |
| Redis db1 | 一份 `AgentContext` JSON | key `agent:ctx:{projectId}:{conversationId}`，TTL 2h，每次 save 重置 |
| LLM | 每轮临时拼的 messages | 无状态，不保留会话 |

### 1.2 `AgentContext` 字段

- `focus` + `focus_stack`：当前锚点与回退栈
- `method_uid`：源码大纲里锁定的方法
- `history`：每轮一条 `{turn, intent, q原话, a≤120字摘要, focus_after}`
- `budget`：轮数、本轮步数/工具次数
- `viewport`：前端屏幕快照（rev、可见节点/边、focusedNode，上限 60）

### 1.3 每轮写入

`_remember` 只在**成功走完主路径**的轮次调用：

- `q` = 用户原话
- `a` = `headline` → 第一个非空 section 正文 → `message`，去换行后截到 120 字
- `focus_after` = 这一轮结束时的 `ctx.focus.uid`
- `budget.turns += 1`

澄清、NAVIGATE、OUT_OF_SCOPE、无锚点、工具失败这些提前 return 的分支**不写 history**。

### 1.4 本轮改动后两个 LLM 看到什么

| | 看到的内容 |
| --- | --- |
| LLM1（意图） | focus、**完整 history**、当前原话、6 个 intent 与规则 |
| LLM2（讲解） | focus/method、屏幕摘要、**完整 history**、用户原话 + 改写提示、工具数据、evidence、uid 白名单 |

改动前 LLM1 只给最近 3 轮，LLM2 完全看不到 history。

## 4. 诊断

### 4.1 六选一没有“回忆”类目

现有 intent：`EXPLORE_OVERVIEW / EXPLORE_FLOW / EXPLORE_RELATION / EXPLORE_CODE / NAVIGATE / OUT_OF_SCOPE`。

“刚才第一个类是什么”“最开始我们聊的那个类”问的是**对话本身**，不查图，六选一里没有对应项。模型只能在现有项里挑一个，然后给低置信度。

### 4.2 两类“回忆”要分开

- **纯对话回忆**：刚才聊了哪个类、上一轮结论是什么、最开始那个类叫什么。  
  → 不需要查图，只需要 history。六选一缺项。
- **指代代码的追问**：刚才那条链的下游是谁、接着刚才那个继续。  
  → 本质仍是 `EXPLORE_FLOW / EXPLORE_RELATION`，只是 `entityRef` 要从 history 里解析。现在 LLM1 的 prompt 只说“有锚点时通常就是 focus”，没告诉它“也可以从历史里找”。

### 4.3 澄清分支不写 history

回忆型问题一旦被误判成低置信，这一轮就完全消失：不查图、不回答、不记录。用户连续追问也无法把上下文补回来。

### 4.4 0.55 不是“模型不会”

它是模型在说“没有合适的类目”。把阈值降到 0.5 会让它带着错误意图去查图，错的图比澄清伤害更大。

## 5. 后续放开路线（未实施）

| 等级 | 放开什么 | 必须先补 | 直接后果 | 风险 |
| --- | --- | --- | --- | --- |
| 0 | 加 `RECALL`；从 history 解析 `entityRef` | LLM1 prompt、RECALL 分支、专门讲解 prompt、测试 | 4 个 0.55 能正常回答 | 低 |
| 1 | 一轮 2–4 步、多次工具（R6） | planner、4 步/6 次预算、去重、终止条件、证据合并、冲突处理、steps UI | 能处理复合问题 | 中，没有预算和去重必乱 |
| 2 | LLM 自选工具（function calling） | 工具 JSON Schema、参数校验、类 uid/方法 uid 区分、审计、prompt injection 防护 | 能处理没有现成 intent 的问题 | 中高，选错工具/传错参数 |
| 3 | 没有工具覆盖也允许回答 | 类级源码、全文/语义搜索、运行时/设计意图/质量数据、能力检查式拒答、评测 | 能答“为什么这么设计”“并发多少” | 高，最容易用常识补出像真的幻觉 |

### 5.1 工具够不够

| 工具 | 能回答 | 缺口 |
| --- | --- | --- |
| overview | 类型、概述、技术栈、模块 | 没有设计意图、质量数据 |
| classes | 类清单 | 最多 40 条；没有模糊/语义搜索 |
| class-relations | 1-hop 上下游（BOTH） | 不展开多跳；不解析 DI/多态 |
| call-chain | DOWN 多层、UP 单层 | 没有 BOTH；撞接口就断；跨服务断 |
| method-body | 方法源码切片 | 需要方法 uid；**没有类级源码工具** |

类级源码接口其实存在（Java `CodeGraphController` 的 `class/source`），但只给前端代码抽屉用，没有注册成 Agent 工具。

**结论**：结构性问答够用；自由问答不够用。

### 5.2 放开后会不会乱套

- 只加 RECALL / history 解析：不会。
- 降阈值：会，错图。
- 多工具：有预算、去重、终止条件就可控；没有就会重复查、超时、答一半。
- 自由选工具：会选错、传错参数，尤其是类 uid / 方法 uid 混用。
- 自由回答：最危险。现有防御只保证 `citations` 和 `uiCommands` 可校验，**正文本身没有结构化校验**；允许图外内容后，正文就是主要幻觉来源。
- 去掉 evidence 白名单：等于拆掉最后一道结构化防线，不建议。

### 5.3 推荐顺序

1. 先做等级 0：`RECALL` + 从 history 取 `entityRef`，阈值保持 0.6。
2. 复杂问题走 R6 有界多步，不要直接自由发挥。
3. 开放范围前先补工具和数据（类级源码、搜索、能力检查拒答）。
4. 先做评测集（30–50 条 golden question），再谈放开。

## 二、决策记录

### 点类看关联：类级聚合，不做到方法级

调用关系在 Neo4j 里是**方法级**的（`CALLS` 连 `Method`），但 P1 的交付是「类级列表」。决定：Cypher 查到方法级边后，Java 侧按「目标类」聚合，每条类级关联附一个**证据字符串**（如 `handleLogin(String) → login(String)`），既保留层次又给前端可读的线索。

### 方法↔类的归属：给 :Method 加 owner 字段

方法节点原来只把 `owner#signature` 拼进 `uid` 字符串，没有独立的所属类字段。为了「方法→类」聚合查询，给 `:Method` 加 `owner` 属性（= 所属类全限定名）。**代价**：旧图没有该字段，需 re-analyze 重新落图。后续 P2 关系图、P3 领域拆分都会用到，一次性补对。

### 核心类筛选：Top 20 关联度，批量一次 LLM

- **核心 = 关联度最高**：`DEPENDS/EXTENDS/IMPLEMENTS` 出入边 + 方法级 `CALLS`（按 owner 聚合到类），`size()` 求四类边数和排序取前 20。
- **批量一次**：把 20 个核心类的骨架（类名/继承/方法签名，每类截断到 8 个方法）拼进一个 prompt，让 LLM 一次输出 `{items:[{qualifiedName, description}]}`，省 token 快。

## 三、点类看关联代码（后端）

### 接口（`CodeGraphController`）

| 接口 | 返回 |
| --- | --- |
| `GET /api/project/{id}/classes` | 类清单（按包名→类名排序） |
| `GET /api/project/{id}/class/relations?uid=全限定名` | 某类的上下游关联 |

> uid 放 query param，避免全限定名里的 `.` 在路径里出问题。

### 返回结构（`ClassRelationsResponse`）

```
center（选中类）
├─ upstream（谁指向我）：callers / dependents / subclasses
└─ downstream（我指向谁）：callees / dependencies / parents
```

6 个方向各一条 Cypher，Java 侧 `aggregateCalls/aggregateDepends/aggregateInherit` 按目标类归并。

## 四、核心类简要描述（后端）

### 流水线新增第四阶段

`AnalysisStage` 加 `DESCRIBE`，百分比重排为 SCAN 0-10 / AST 10-50 / OVERVIEW 50-80 / DESCRIBE 80-100。执行顺序 `SCAN → AST → OVERVIEW → DESCRIBE`（描述是语义增强层，放概况之后）。

### `ClassDescriptionServiceImpl` 四步

1. `queryCoreClasses`：Cypher 取 Top 20 核心类（uid/name/pkg/kind）+ 骨架（父类/接口 + 方法签名）
2. `buildPrompt`：组装骨架 prompt，要求 LLM 原样保留 qualifiedName、只输出 JSON
3. `callLlm`：`ChatClient.create(chatModel)...entity(ClassDescriptionBatch.class)` 一次批量
4. `writeBack`：`UNWIND + MATCH + SET c.description` 写回

幂等靠 astStage 每次清图重建，describeStage 在其后重写，天然覆盖。

## 六、踩坑：Cypher 聚合分组错误（42I18）

核心类查询最初用多个 `OPTIONAL MATCH` + `count()` 叠加，最后 `WITH c, out + in + outCalls + count(r4) AS score` 把聚合表达式和非分组表达式混在一起，Neo4j 报 `Aggregation column contains implicit grouping expressions`。

**修复**：改用 `size([...])` 模式推导，一次算四类边数——无聚合分组问题，且避免了多路 `OPTIONAL MATCH` 的笛卡尔积。

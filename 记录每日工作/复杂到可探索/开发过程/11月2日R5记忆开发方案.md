## 0. 一句话定位

R5 的记忆补的是**会话之外的用户状态**：跨会话记得用户上次查到哪、结论是什么、哪里没查完。

`agent_context` 解决"现在是什么状态"，`agent_turn` 解决"这一轮发生了什么"，`agent_memory` 解决"下次开新会话带什么过来"。**它必须比对话小得多**，否则只是把 2h TTL 换成了永久 TTL。

### 1.2 由现有机制唯一推出（不是选择题）

| # | 结论 | 推导 |
|---|---|---|
| B1 | **记忆不进 `citations`** | `citations` 定义是"本轮 Java 从当前图捞到的 evidence 子集"。放记忆进去要么被 `split_citations` 丢弃，要么放宽白名单导致 A2 失效，形成"提议→记忆→引用"的自我强化环 |
| B2 | **蒸馏来源是 `agent_turn` 结构化列** | `ctx` 会被 `prune_window` 删除 TOOL/RETRIEVAL，且 `ctx.turn` 不进快照；Response 没有 evidence/rev/outcome；transcript 是渲染文本 |
| B3 | **独立 Qdrant 集合** | 共用集合时 `delete_other_revs` 会按 `rev != activeRev` 把记忆全删；`count_project` 会数多，破坏 R4 的数量校验 |
| B4 | **记忆查询不带 `activeRev` 过滤** | 类是"某一版图的快照"，记忆是纵向用户状态 |
| B5 | **`subject_uids` ⊆ 当轮 `evidence_json`** | 与 citations 同源：任何路径都不能创造新的图事实 |
| B6 | **检索由代码触发，LLM 只消费结果** | LLM 不知道记忆库里有什么；同一问题两次触发不一致会让评测失效 |

## 3. 数据模型

### 3.1 `agent_memory`（新增）

```sql
CREATE TABLE agent_memory (
  id                     BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id                BIGINT       NOT NULL,
  project_id             BIGINT       NOT NULL,
  scope                  VARCHAR(16)  NOT NULL,   -- PROJECT（v1 只用这个）
  type                   VARCHAR(16)  NOT NULL,   -- v1 只写 FACT / OPEN_QUESTION
  text                   TEXT         NOT NULL,   -- 一句原子断言，<=120 字
  text_hash              CHAR(64)     NOT NULL,   -- 归一去重用
  primary_subject_uid    VARCHAR(512) NULL,       -- 单值，供精确查询
  subject_uids           JSON         NOT NULL,   -- 全量，evidence 子集
  graph_rev              INT          NOT NULL DEFAULT 0,
  confidence             DECIMAL(4,3) NOT NULL DEFAULT 0.5,
  trust                  VARCHAR(16)  NOT NULL,   -- explicit / distilled
  status                 VARCHAR(16)  NOT NULL,   -- active / stale / expired / superseded / rejected
  superseded_by          BIGINT       NULL,
  source_conversation_id VARCHAR(64)  NULL,
  source_turn_no         INT          NULL,
  use_count              INT          NOT NULL DEFAULT 0,
  last_used_at           DATETIME(3)  NULL,
  expires_at             DATETIME(3)  NULL,
  created_at             DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at             DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                          ON UPDATE CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_memory_dedup (user_id, project_id, scope, type, text_hash),
  KEY idx_memory_owner (user_id, project_id, status, type),
  KEY idx_memory_subject (user_id, project_id, primary_subject_uid, status)
);
```

说明：

- `primary_subject_uid` 单列出来，因为 `subject_uids` 是 JSON，**按 subject 精确查不能用 JSON 模糊匹配**。
- 唯一键用于**合并幂等**。
- 软状态，不物理删。

### 3.2 `agent_turn` 增列

```sql
ALTER TABLE agent_turn ADD COLUMN memory_distilled_at DATETIME(3) NULL;
ALTER TABLE agent_turn ADD KEY idx_turn_distill (memory_distilled_at);
```

### 3.3 Qdrant `archmind_memories`（新增集合）

| 项 | 值 |
|---|---|
| vectors | `dense` 1024 Cosine + `sparse`（同一次 embed 同时产出） |
| payload | `userId` / `projectId` / `type` / `status` / `primarySubjectUid` / `graphRev` / `text` |
| payload index | `userId`(int) / `projectId`(int) / `type`(kw) / `status`(kw) |
| 查询过滤 | userId AND projectId AND `status='active'`（**不带 rev**） |
| point id | memory 行 id 的 uuid5，保证重复 upsert 幂等 |

**失效即删点**：D11 决定 stale 不注入，所以状态迁移到非 `active` 时直接删掉 Qdrant 点，MySQL 行保留。不能让索引里存在一条 MySQL 已判定失效的点——过滤条件写错一次就会漏出去。

## 4. 写入路径

### 4.1 v1 的两条路径

```
用户显式 ──┐
           ├──→ 校验(B5: subject ⊆ evidence) ──→ 合并/复活 ──→ agent_memory ──→ Qdrant
会话结算 ──┘
```

| 路径 | v1 | 产出 | 状态 | 失败影响 |
|---|---|---|---|---|
| 用户显式 | 是（语言触发） | FACT / OPEN_QUESTION | `active` | 回答照常 |
| 会话结算 | 是（空闲 30 分钟） | FACT / OPEN_QUESTION | `active` | 不影响本轮，标 `memory_distilled_at` 留待重试 |
| 在线逐轮蒸馏 | 后置 | — | — | — |
| LLM 提议 | 后置（管理 UI 之后） | — | — | — |

**偏好和纠正在 v1 不写**。因此 v1 **不需要任何确认弹窗**：能写进记忆的只有"用户自己说的话"和"从流水蒸馏出的事实/未决问题"，后两者错了代价小、有 rev 约束。

#### 显式入口（v1 只有语言触发，无前端改动）

触发词：`记住 / 记一下 / 记下来 / 备注一下 / 别忘了`。

命中后的行为：

1. 只把**本轮 `evidence_json` 覆盖的事实**写成 FACT。没有 evidence 就不写——这是 B5 的天然兜底，也能挡住"这不是我的问题"这类误命中。
2. 写入后在本轮 `message` 末尾追加一行注记（`（已记住：…）`），作为唯一反馈。不改 `sections`、不改 `citations`、不新增响应字段，所以前端零改动。
3. 注记随 `message` 进入 `messages`，下一轮模型能看到，不需要额外机制。
4. v1 没有删除入口；写错了靠后续合并、失效或管理界面（后置）纠正。这是"只做语言触发"的已知代价。

---

### 4.2 蒸馏输入过滤（原闸门）

由于在线逐轮蒸馏后置、偏好取消，闸门的角色变了：**它不再决定"要不要调用蒸馏"，而是决定"哪些轮次进入蒸馏器的输入"**。

**硬跳过**（不进输入）：

- `outcome == NAVIGATE` / `REFUSE`
- `len(question.strip()) < 4`
- `evidence_json` 为空 **且** `retrieval_json` 无候选
- `memory_distilled_at != null`

其余轮次连同其结构化字段一起进入该会话的输入序列。

**计数规则保留，但移入蒸馏 prompt 的判定提示**：

- 同一 `subject_uid` 在序列中出现 ≥2 次 → 值得成一条事实；
- `CLARIFY / NEED_ANCHOR / TOOL_DOWN` 连续两轮 → 值得成一条未决问题。

这两条现在是"提示模型怎么判断"，不是"决定是否调用"。

### 4.3 提取逻辑（distiller 的判定清单）

按顺序过，任一条不满足即降级或丢弃：

1. 这条信息下次只查图能不能得到？能 → 丢弃（**控制增长的第一道闸**）。
2. 有当轮 `evidence_json` 支撑吗？`subject_uids` 必须 ⊆ evidence，否则丢弃。
3. 和已有记忆重复吗？重复 → 合并。
4. 超过该类型容量了吗？超 → 淘汰最久未使用的。
5. 输出 0 条是正常结果；**一个会话通常只产 1–3 条**。

### 4.4 合并与复活

按 `(user_id, project_id, scope, type, text_hash)` 查重：

| 命中的行 | 处理 |
|---|---|
| `active` 且相似 | UPDATE（刷新 text / confidence / updated_at） |
| `stale` 且**新 rev 更高** | **复活**：`status → active`，更新 `graph_rev`。同 rev 的积压回合不复活——它证明不了新图里还有这条 |
| `expired` / `rejected` | 尊重人的决定，不自动复活 |
| 无命中 | INSERT |

复活规则解决的是"一次重新分析把记忆全判死"的问题：只要下次蒸馏产出了同样的事实，它就会在新 rev 下回来。

## 5. 读取路径

### 5.1 召回来源（v1 取消 L0 常驻包）

| 级别 | 内容 | 触发 | 上限 |
|---|---|---|---|
| **冷启动** | 按第一问召回 | `budget.turns == 0` | 3 条 |
| **事件触发** | top-k 召回 | 见 5.2 | 1–3 条 |
| **工具触发**（R6） | `recall_memory(query)` | 模型主动 | 预算内 |

取消 L0 的理由：它原本承载的是偏好和纠正，两者 v1 都不做。事实和未决问题走检索就够，不需要每轮常驻。

### 5.2 触发条件

```
window_entities = ctx.focus ∪ ctx.method_uid
                ∪ {最近 K 条 messages[].meta.citations 的 uid}
                ∪ {窗口内 retrieve 消息的候选 uid}
```

| # | 条件 | 场景 |
|---|---|---|
| 1 | `budget.turns == 0` | 冷启动，对第一问召回一次 |
| 2 | `last_outcome == "CLARIFY"` | 上一轮没问清，这轮先看看记忆 |
| 3 | 出现跨会话说法（上次 / 之前 / 刚才） | 「上次那个支付回调」——**不看窗口**，它本来就在说窗口之外 |
| 4 | 出现弱指代（它 / 那个 / 接着 / 继续）**且** `window_entities` 为空 | 这句话在接什么，窗口里找不到 |
| 5 | 类检索候选为 0 **且** `ctx.focus is None` | 记忆可能知道用户说的是哪个类 |

`window_entities` 只算**本轮之前**的窗口（`messages[:turn_start]`）：把本轮刚检索出的候选算进来，「指代无着落」就永远不会成立。

**不触发**：有 `focus` / `method_uid`（与 `_retrieve` 的规则一致）。

**记忆实体如何成为锚点**：记忆里的 `subject_uids` 进入 entityRef 的白名单（`resolve_entity_ref` 的 `extra_uids`），但只在"本轮检索给出了别的候选"时才参与核对；检索为空时维持 R4 原有的"不做约束"。

### 5.3 注入方式

- 记忆块单独成段，标 **"记忆参考（未查证，不是证据）"**，与现有 `_reference_block` 同构；
- 记忆候选**不参与** `anchorScore`，只作为 `entityRef` 的补充来源；
- 每次注入后回写 `use_count` / `last_used_at`——这是容量淘汰和"哪些记忆真的有用"的唯一依据；
- **只注入 `status='active'`**，stale / expired / superseded / rejected 一律不出现。

## 6. 与 citations 的边界

已在 B1 论证，结论：

- `citations` = 本轮 evidence 子集，记忆永远不进；
- 记忆只能做三件事：**背景注入**、**检索种子**、**措辞**（"据你上次所说…"）；
- 一旦要作为本轮结论，必须回图查一次，变成 evidence 才能 citation。

## 9. 灰度与回退

- `settings.memory_enabled` 总开关，默认关闭灰度；

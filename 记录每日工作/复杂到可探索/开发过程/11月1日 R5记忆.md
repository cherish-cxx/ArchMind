首先需要的效果：
1. 隔天新开会话，用户说“接着上次的支付流程往下看”——它知道上次查到哪个类、结论是什么、哪里是断点。
2. 说过一次的偏好不用再说——“先给结论再展开”“别每次都画图”。
3. 用户纠正过的不再犯——“这个项目里 OrderService 有三个实现，默认 impl 是错的”，下次不要再默认。



长期记忆内部分类：
- **偏好**：影响“怎么答”（先结论、不要图、中文）。只能用户显式或明确确认。读法：常驻，不做向量检索。
- **事实/结论**：图里查过、用户认可的判断，例如“支付回调入口是 X，Y 是跨服务断点”。带 rev，rev 变了降级。读法：按需检索。
- **纠正**：用户否定过的东西，优先级高于事实和模型默认。读法：回答前按 subject 精确查，**不能只靠语义检索**——漏一条就白存。
- **未决问题**：这轮没查完、用户说下次再说。驱动 suggestion。

一条关键边界：**图能查到的不进记忆**。否则同一事实两个真相源，rev 之后必然打架。记忆只存图里没有的：用户视角的意图、偏好、判断、别名、结论。

三条路径：
- 用户显式：说一次用户生效？
  触发是 UI 按钮、“记住…”、或 R6 的 `remember` 工具。零 LLM、确定性、直接 `active`、可审计。覆盖率最低，但纠正和偏好只能靠它
- 蒸馏：用户什么都不说，系统也有记忆
  实际是一轮落库后一步跑，或者会话结束，离线性。输入必须是 `agent_turn`（结构化地带 question / answer / evidence / rev / outcome），不是前端聊天记录——聊天记录没有 rev、没有角色区分。输出是**候选单元**，`status=proposed`。
- LLM提议：回答的当下顺手抓住？
  “这条值得记”的信号，只有模型在看完整上下文时才有。形式是 R6 的 `propose_memory` 工具或回答后的 proposals 字段。它不阻塞本轮、不参与本轮 citations；高影响项（偏好、纠正）要用户确认。

记忆检索：
先说什么情况**不需要**，这才是设计重点：

- 会话窗口内、有 focus、问的是图里有的实体 → 工作记忆就够了。
- 每轮无脑 top-k 会带噪声；而且 bge-m3 分数挤在 0.40–0.75，记忆和类卡片混在一个集合里会互相抢排序。

需要检索的四个触发点：

1. **冷启动 / 跨会话第一问**：Context 已过期，加载时注入固定小包（偏好 + 最近 3–5 条结论，≤10 条）。
2. **指代超出窗口**：“上次那个支付回调” → 记忆补 `entityRef` 候选，再去图里查。
3. **回答前纠错检查**：按 subject uid 精确查纠正类记忆。
4. **生成 suggestion**：从未决问题里取。

当前主流 agent 的做法：

- **Mem0**：每轮抽记忆 → 与相似记忆比对 → ADD / UPDATE / DELETE，重点是冲突合并。
- **Zep / Graphiti**：时序知识图谱，事实带 `valid_at` / `invalid_at`，能回答“什么时候是真的”。
- **MemGPT / Letta**：core memory 常驻 + archival memory 用工具检索，即“小常驻 + 按需”。
- LangGraph 的 checkpointer 不是记忆，是会话状态。

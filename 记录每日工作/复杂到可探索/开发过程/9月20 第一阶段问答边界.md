# 9月20 第一阶段问答边界（Agent v1 能解决什么问题）

> 承接 [9月19 Agent v1设计](9月19%20Agent%20v1设计.md)。
> 9/19 定的是「Agent 放在哪、怎么协作」；**本篇只定一件事：第一阶段用户提问后，Agent 能解决到哪。**
> 结论先给：**V1 的边界不是"限制用户问什么"，而是"入口必须先有锚点"。**

---

## 1. 先看清 Agent 在哪一环介入

整个用户使用过程是一个闭环：

```
① 上传项目 zip
      ↓
② 系统分析（AST + LLM，只做一次）
      ↓
③ 项目变成「可探索的地图」：概况 + 类清单 + 类间关系
      ↓
┌──→ ④ 用户点一个类（或直接在 AI 面板问一句）
│         ↓
│    ⑤ Agent 回答，一次给三样东西：
│       · message      讲解文字
│       · uiCommands   图跟着动（高亮 / 展开 / 画调用路径）
│       · suggestions  下一步能点什么
│         ↓
│    ⑥ 用户顺着往下走：点图上的节点 / 点建议 / 直接追问（"它的调用方呢"）
│         ↓
└──── ⑦ 焦点切到新类，Agent 带着上文回答下一轮 → 回到 ⑤
      ↓
⑧ 看够了 → 退出（或换个项目 → 回 ①）
```

**闭环是 ④→⑤→⑥→⑦→④**：上一轮的输出（讲解 + 图变化 + 下一步入口）成为下一轮的输入。
①②③ 是一次性铺垫，⑧ 是出口。

> 这个环要转得动，靠三样东西缺一不可：`uiCommands` 让图真的动、`suggestions` 让用户知道往哪走、`Context` 记住用户现在看着哪个类。**少任何一个，④ 都回不去，环就退化成一次性问答。**

**边界问题就出在这里**：⑤ 能不能答对，取决于 ④ 用户给的是不是一个**能落到图上的实体**。

---

## 2. 边界 = 5 个工具能落到的 × 图里真实存在的边

### 2.1 图里到底有什么（今天核实的）

AST 提取范围（`AstParserServiceImpl`）：类 / 接口 / 枚举（**含嵌套类型**）、全部方法 + 构造器、全部字段；**没有可见性过滤**（private / static 也提取）。

所以——**声明层是完整的，边界不在"抓得全不全"，而在"有哪几种边"**：

| 有 | 没有 |
| --- | --- |
| `CALLS`（直接调用，带 count） | DI / 多态：`@Autowired` 接口调用走哪个实现 |
| `EXTENDS` / `IMPLEMENTS` | 反射 / 动态代理 / SpEL |
| `DEPENDS`（字段、参数类型） | lambda 与匿名内部类里的调用 |
| 类 / 方法 / 字段声明 | 外部 jar（设计上就丢弃：宁可漏不要错） |
| | 配置装配（`application.yml` / `@Bean`） |
| | 业务领域（`Domain` / `IN_DOMAIN` 边，P3 才有） |

### 2.2 提问 × 能不能答

| 用户问的话 | 能不能答 | 卡在哪 |
| --- | --- | --- |
| 这个项目是做什么的 / 什么技术栈 | ✅ 能答好 | `overview` 表，独立于图 |
| 项目里有哪些类 | ✅ 能答 | `classes` |
| X 类依赖谁 / 谁依赖 X / 继承谁 | ✅ 能答好 | 1-hop，`class-relations` 已有 |
| X 类是干嘛的 | ✅ 能答（一句话） | `:Class.description`，核心类才有 |
| X 这个方法怎么实现的 | ✅ 能答好 | `method-body` 磁盘切片，**这是最深的一层** |
| A 调到 B 这条链路 | ⚠️ 答一半 | `CALLS` 只有直接调用，**撞到接口就断** |
| **业务流程是什么**（核心场景） | ⚠️ 答一半 | 同上一行，且 Spring 项目**必然**撞接口 |
| 为什么不这么设计 / 这样写有什么问题 | ❌ 答不了 | 图里没有设计意图、没有质量数据 |
| 「处理订单的地方在哪」（不报类名） | ❌ 答不了 | **无 embedding，没有语义入口** |
| 这个接口并发量多少 / 会不会死锁 | ❌ 答不了 | 只有静态结构，没有运行时 |
| X 属于哪个业务模块 | ⚠️ 降级答 | 模块是 LLM 看 pom+README 编的假节点（B5） |
| 写个接口 / 改一下这段代码 | ❌ 直接拒 | `OUT_OF_SCOPE` |

**一句话概括**：*能回答"图里有的东西"——谁调谁、谁依赖谁、这个方法怎么写的；不能回答"图里没有的东西"——为什么这么设计、这个项目处理什么业务、写得怎么样。*

## 3. 最要命的一道墙：接口（DI）

这不是小瑕疵，是**主流 Java 项目的常态**：

```
OrderController  ──CALLS──▶  OrderService（接口方法，无方法体）
                                    ✗ 断在这里
                             OrderServiceImpl ──▶ OrderMapper ──▶ DB
```

`@Autowired OrderService orderService` 的字段类型是接口，所以边指向**接口方法**；接口方法没有方法体，**没有出边**。下半条链（实现 → Mapper → 库）整个看不见。

**影响面**：`EXPLORE_FLOW`（业务流程）是设计的核心场景，而它在真实 Spring 项目里**大概率只能讲 1–2 跳就断**。设计文档里的 `gaps` 就是为这个准备的——但**"诚实地断"和"能往下讲"是两回事**。

> ⏳ 待确认：具体断法（是停在接口方法节点，还是整条边被丢弃）需要 P1 打真实 hmall 数据看一次，不要凭推断下结论。

### 便宜的补救：接口处按 `IMPLEMENTS` 扇出

**不用动 AST**——`IMPLEMENTS` 边已经在图里了（hmall 有 16 条）。`call-chain` 走到接口方法时，不报 `NO_DOWNSTREAM_EDGE`，而是顺 `IMPLEMENTS` 返回实现类：

> "OrderService 是接口，实现类有 `OrderServiceImpl`（唯一），下面讲的是它的实现。"

**死路 → 分支点**，核心场景的可用深度直接翻倍。建议放进 P1 和 `call-chain` 一起做——**它决定了 Agent 是"能讲业务"还是"只能念签名"**。

## 4. 结论：第一阶段没法给高自由度，入口必须收窄

**问答质量 ≈ 用户有没有先给一个锚点。**

| 情况 | 结果 |
| --- | --- |
| **给了锚点**（在图上点了一个类，focus 有值） | 代词"它"能消解，方向明确，5 个工具全用得上 → **V1 主战场** |
| **没给锚点**（空白框里打一句话） | 只能靠 LLM 在类清单里猜类名。猜中就好，猜不中就拒绝 |

所以第一阶段不做「自由问答」，做「**先选类，再提问**」：

1. 首屏默认聚焦一个类（或提示用户先点一个）
2. 类名对不上时，兜底走 `classes` 让 LLM **在清单里选**，而不是硬猜
3. 真答不了的（语义模糊 / 设计评价 / 运行时），走 `OUT_OF_SCOPE` 一句话拒掉 + 给两个能点的 `suggestion`

> ⚠️ 根因是 **DeepSeek 无 embedding 接口**（F1），语义入口做不了。换 Qwen / 智谱排 P3。
> **这条要写进验收预期**，别到演示时才发现"用户得说对类名"。

---

## 5. 落到 P2 验收预期

| 项 | 预期 |
| --- | --- |
| 主场景 | **先点类 → 再提问**，能连续多轮（闭环成立） |
| 流程类问题 | 深度 1–2 跳；撞接口时按 `IMPLEMENTS` 扇出继续；断链必须显式说"未解析到下游" |
| 语义类问题 | **不保证**——用户必须说对类名，或让 LLM 在类清单里选 |
| 设计评价类 | 直接拒（`OUT_OF_SCOPE`），给引导 |
| 演示口径 | curl 可演示即可；两轮（第二句用代词）能对上 focus 就算闭环跑通 |

1. **快照漂移（重要）**：项目 1 的索引有 104 个顶层类（main 97 + test 7）；当前源码 main 155 + test 16。索引少 **58 个 main + 9 个 test，共 67 个**，多 0 个。

2. 描述来源 100% 为 LLM，没有 FALLBACK；说明描述补齐链路是完整的。

### 3.3 卡片拼装：Python 侧放了什么，缺的是什么

Python 侧拼卡片的唯一入口是 `app/core/indexer.py:49-63`：

```python
if description:
    return f"{node.simple_name}：{description}", "LLM"
```

也就是说，**有描述的类（本次 104/104）进入向量的文本只有「类名：一句话描述」**；`packageName`、`kind` 只在 payload 里，没有进向量。没有描述时才用 `"{类/接口/枚举} {simpleName}，位于包 {package}"` 兜底。

实际卡片（从 Qdrant payload 还原）：

| 类 | 实际卡片文本 |
| --- | --- |
| `SecurityConfig` | `SecurityConfig：配置安全过滤链、密码编码与跨域策略。` |
| `JwtAuthenticationFilter` | `JwtAuthenticationFilter：拦截请求并校验JWT完成用户认证。` |
| `RelationResolver` | `RelationResolver：解析代码中类、方法调用与继承等关系` |
| `CodeGraphQueryServiceImpl` | `CodeGraphQueryServiceImpl：查询代码图谱中的类节点与关系数据` |

Python 侧**拿不到**方法名/签名/上下游，不是拼装时漏了，而是契约里没有：

- `ClassNode`（`app/models/tool.py:108-120`）只有 `qualified_name / simple_name / package_name / kind / description / is_abstract / core / file_path / start_line / end_line`；
- Java 的 `ClassNodeDTO`（`ClassNodeDTO.java:10-35`）字段完全一致，也没有 methods / signature / relations；
- 方法在 Neo4j 里是独立的 `:Method` 节点（`CodeGraphNeo4jWriter:66-72`），`/internal/tools/classes/page` 只返回 Class 节点属性。

所以卡片不全有两层：

1. **Python 侧可修的小缺口**：`packageName`、`kind` 已经拿到了，却没进卡片文本。补上成本很低，但预期收益有限（同包类很多，`kind` 只帮接口/实现类消歧）。
2. **Java 契约缺口（主要）**：方法名/签名/上下游根本不在 `ClassNodeDTO` 里。Python 无法单方面补；要让卡片包含这些，必须先扩 `/classes/page` 的返回（例如 `methodNames`、`upstreamSummary`、`downstreamSummary`），或者新增一个批量关系接口。
3. **AST 缺口（独立）**：record 类型不解析，`ParsedCall` 等 6 个 record 在所有索引里都缺席。

### 3.4 卡片契约：已实现（待集成验证）

新增 `GET /internal/tools/classes/cards?projectId&afterUid&limit`，返回 `ClassCardPageResponse`：

- `ClassCardDTO extends ClassNodeDTO`，补 `methods / methodCount / upstream / downstream / *Truncated`
- `MethodBriefDTO`：`name / signature / visibility / isStatic / isConstructor`
- `UpstreamDTO`：`callers / dependents / subclasses`（各带 count）
- `DownstreamDTO`：`callees / dependencies / parents`（各带 count）

批量方式：**每页 1 次基础分页 + 7 条集合查询**（方法 1 条，上游 3 条，下游 3 条），不是逐类 6 条。方法按 `Method.owner` 聚合；上下游按本页 uid 集合聚合；方法 cap 10、每类关系 cap 5，另带全量 count 与截断标记。新增 `Method(projectId, owner)` 索引。

Python 侧同步：`ClassCard/ClassCardPage` 模型、`JavaClient.class_cards_page`、Indexer 改用卡片接口；`build_card` 最多拼 8 个方法名；payload 存 methods/upstream/downstream；LLM1 候选块展示最多 5 个方法名。

**验证状态**：
- Java `mvn compile` 通过；`CodeGraphQueryServiceImplTest` 新增卡片聚合用例通过（mock Neo4j）。
- Python `154 passed / 5 skipped`。
- **未做真实 Neo4j 集成验证**：实验室 7687/7474 未对外暴露，无法在本地执行新 Cypher。
- **未重跑索引**：线上 Java 还是旧版本，没有 `/classes/cards`；在新 Java 部署前调用会失败。现有索引仍是旧点（没有 methods/上下游）。

结论：**主锚点基本都能定位，次要锚点容易丢**。如果把「锚点 recall」理解为「入口能不能找到」，当前是 95%；如果要求「所有相关类都进前 5」，则 79.6%，差一点。

### 4.4 标识符子集（12 条）

hybrid / dense / sparse / DBSF **全部 100% recall@1**。这组数据在当前 104 类的规模下已经饱和，无法区分融合方式。

但它暴露了一个更实质的问题：**卡片里只有类名 + 描述，没有方法名/签名**。所以「`cleanToken` 这个方法在哪」这类方法级问题，检索层根本无法定位——不是排序不好，而是索引里没有这个可检索单元。

### 4.5 负样例与「能不能用分数拒答」

8 条域外问题的 top1 RRF 分：0.50、0.57、0.67、0.70、0.75、0.75、0.83、0.83。正样例的 RRF 分也大量落在 0.5–0.8。

- 这说明 **RRF 分是名次融合分，不是相似度，不能设阈值**（代码注释里已经写明，本次用数据确认）。
- 检索层不做拒答；域外问题仍会返回 5 个候选。必须在 LLM1 意图判定或候选相关性判定里挡住，否则会把无关类塞进 prompt。
- 另一个副作用：RRF 同分非常常见，Qdrant 对同分点的返回顺序不保证稳定。评测脚本已按 `(-score, uid)` 定序，保证数字可复现；生产候选顺序不影响正确性，但会影响「用户看到的前 5」的稳定性。

**本轮实施的四处改动**

1. `retrieve_top_k` 5 → 10（`app/config.py`），修窗口截断。
2. 候选规则改成「先判断问题类型，再按类型选」（`app/core/prompt.py`）：配置类 / DTO / 流程入口 / 查询服务 / 解析器 / 实现类分别有优先序，替代原来一律偏好 Controller/Service 的规则。
3. 新增 `slots.anchorScore`（0–3）与 `ANCHOR_MIN_SCORE=2`（`app/models/intent.py`、`app/core/loop.py`）：分数不足时按无锚点处理，不再硬选。本次 40 条全部给了 2/3 分，门槛没有触发，但把「意图置信度」和「锚点匹配度」分开了。
4. 澄清文案改为给出前两个候选及其类型/描述（`app/core/loop.py:_need_anchor`），不再是泛化的「请先点一个类」。

**结论：主要瓶颈是「LLM1 在候选里选入口」，不是检索召回。** 窗口、选择偏差、类型偏好三个原因分别由 top-10、类型化规则、anchorScore 处理；改后主锚点 80% → 90%，任意锚点 90% → 100%，域外拒答保持 8/8。

## 五、发现的问题（按优先级）

### P0 — 入口选择错误（已修复并复测）

4 条错选拆开看（改动前 top-5）：

- **窗口截断（2 条）**：Q04 的 `JwtAuthenticationFilter` 排 6、Q22 的 `CodeGraphQueryServiceImpl` 排 8，top-5 根本看不到。
- **选择偏差（2 条）**：Q01 的 `SecurityConfig` 排 5、Q02 的 `LoginResponse` 排 1，正确类都在候选里，LLM 却选了更泛的 Service。

已实施：`retrieve_top_k` 5 → 10 + 类型化候选规则 + `anchorScore` 门槛 + 定向澄清。复测结果：主锚点 **36/40（90%）**、任意锚点 **40/40（100%）**、选错 0、负样例 8/8 拒答（详见 §4.6）。

### P0 — 索引快照落后当前源码（数据状态，不是机制缺陷）

现有索引的图快照约等于 2026-09-14 的源码（对齐提交 `930f23b`），比当前源码少 67 个顶层类（含 R4/R6 新增类）。本次评测只能覆盖快照内的 104 个类。
真实用户上传后不会再改源码，所以这不是产品缺陷；但如果要声称「当前代码的可检索性」，必须先重新 analyze → describe → index。**动作**：对当前代码重跑一次，用同一份评测集复测。

### P1 — 实体卡片信息不足（契约已实现，待部署 + 重跑索引验证）

路线图 R4 写的是「实体卡片：Class/Method 的名称、包、签名、描述、上下游一句话」，修复前的实现（详见 §3.3）：

- **Python 拼装**只用了 `simpleName：description`；`packageName`、`kind` 已在 `ClassNode` 里，却没进卡片文本；
- **Java 契约**（`ClassNodeDTO`）没有 methods / signature / relations，方法在 Neo4j 里是独立的 `:Method` 节点；Python 无法单方面补；
- **AST** 不解析 record，`ParsedCall` 等 6 个 record 在所有索引里都缺席。

因此方法级查询（「cleanToken 在哪」「register 方法怎么校验」）无法定位。

**已实现**：新增 `/internal/tools/classes/cards` 批量接口与 Python 消费链路（§3.4），卡片文本追加最多 8 个方法名，payload 带 methods/upstream/downstream。
**待验证**：部署新 Java → 重跑 analyze + index → 用 `run_entry_eval.py` 复测 Q04/Q22，确认方法名让“查询服务 vs 解析器”的区分更稳。
**未做**：record 解析（按要求先忽略）。

### P2 — 混合检索未被证明优于单路

实际实现是 dense + sparse 两路 RRF；清单里的「名称/包关键词通道、图度数先验、可选 rerank」都没有独立实现。

本次数据上：dense 略优于 hybrid（80.0% vs 79.6%），DBSF 最好（82.1%）。样本只有 40 题，差距在 1 题量级，**不足以断言「该换融合方式」**，但足以断言：

- 在「自然语言语义入口」这类问题上，稀疏分支没有带来增益；
- 标识符子集已经饱和（四种方式全 100%），证明不了稀疏分支的价值；
- DBSF 值得在扩样本后做一次 A/B，再决定是否替换 RRF。
